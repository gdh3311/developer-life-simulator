# Developer Life Simulator 시나리오 제작 기준

기획 버전 0.1 · 2026년 11월 23일

출시 본편의 이야기 목표는 12개 챕터와 96개 주 업무를 끝까지 연결하는 것이다. 긴 이야기를 만들면서도 회사별로 전체 게임을 두 벌 제작하거나, 모든 근무일을 채우는 방식은 사용하지 않는다. 분기는 담당 역할, 관계, 준비한 도구와 후속 장면을 바꾸고 공통 사건으로 다시 만난다.

이 문서의 출시 기준은 프로젝트 내부의 품질 기준이다. Steam의 최신 제출 정책이나 법적 요구사항을 대체하지 않는다. 실제 스토어 제출 직전에는 해당 절차를 별도 작업으로 확인한다.

## 현재 구현과 새 계획의 경계

| 영역 | 현재 확인된 구현 | 장편 계획에서 필요한 변화 |

| 인물 | Alex, Daniel, Mina, Sophie, 리크루터, AI | 단계적으로 등장하는 8명의 새 주요 인물 |

현재 이 계획 문서의 추가만으로 게임 구현이 달라지지는 않는다. 특히 새 장기 상태 키를 기존 세이브에 바로 넣거나, 현재 플레이 중인 Git 기록을 초기화하지 않는다.

## 기존 설정을 연결하는 수정

### 시간과 첫 평가

현재의 Day 1~4는 데모의 가속된 인턴 경험으로 보존한다. 신규 본편에서는 이를 첫 달의 대표 근무일 네 번으로 재배치한다. 일차 실행 인덱스와 서사 날짜를 분리하고 근무일 사이에 시간 경과 카드를 넣는다. 스토리 연도는 상대 연차로 보여주며 실제 PC 날짜에 종속시키지 않는다.

현재 마지막 면담의 4일 정규직 전환은 본편에서 첫 달 평가로 옮기고 정식 전환을 챕터 3에 둔다. 기존 세이브가 전환 결과를 이미 갖고 있으면 선행 평가와 전환 사실을 인정한다. 플레이어를 다시 인턴으로 강등하는 마이그레이션을 하지 않는다.

### 채용과 이직

기존 데모의 리크루터는 입사 초반에 연락하고 면접 장면 없이 정식 오퍼를 줬다. 현재 신규 진행에서는 마지막 선택을 면담 지속 제안으로 바꿨다. `offer_stage=interview`로 실제 이직과 구분하며, 기존 저장의 정식 오퍼 선택은 변경하지 않는다. 초반 연락의 포트폴리오·커피챗 맥락 보강, 챕터 3 면담과 기술 검토, 챕터 5 실제 오퍼는 후속 제작이다.

기존 Brightloop 이동 엔딩을 본 플레이어는 선택을 유지한 채 “이직 전 NEXORA의 업무 기록”으로 챕터 2에 진입한다. 현재 결과 화면에서 이 연결을 명시한다. 후반 챕터 전체를 긴 인수인계 기간으로 간주하지 않는다. 챕터 6 이후의 이동 연결과 오퍼 재질문 생략은 아직 구현하지 않았으며, 이 경로의 장기 서사 연결은 후속 검토 대상이다.

기존 엔딩 세이브의 재개는 완료된 Day 4를 반복 실행하지 않는 전용 연결 미션으로 처리한다. 누락된 업무 증거는 거짓으로 채우지 않고 간단한 대조·인계 과제로 보완할 수 있게 한다.

### 권한과 책임

현재 위키는 시니어만 최종 승인·병합한다고 설명하지만 일부 대사는 Sophie가 직접 병합한 것처럼 말한다. 최종 승인자는 Daniel, 변경 작성자는 Sophie로 표현을 맞춘다. 동료의 실수를 주니어 한 사람 탓으로 몰지 않는다.

Daniel의 휴가 중 로그인 장애는 당직 SRE 또는 지정된 시니어가 배포 권한을 가진 것으로 명시한다. 플레이어는 증거 수집과 검증된 패치를 맡고 운영 종료 책임을 혼자 떠안지 않는다. 후반에 권한이 늘면 실제 UI의 승인 가능 범위도 함께 바뀐다.

### 실패의 비용

게임성 개선에서 CI 실패에 일괄 적용되던 기술 신뢰 하락을 제거했다. 장편에서는 로컬 실험, PR 검증, 사전에 합의한 시범 적용, 검증 없이 운영에 반영한 경우를 구분한다. 실패 횟수 하나로 학습을 벌주지 않는다. 현재 구현한 조사 노트와 후속 계획은 [게임성 설계](GAMEPLAY.md)에 정리한다.

미션에서 테스트 추가 줄 수만 세거나 특정 문자열을 찾는 판정은 가능한 범위에서 동작 계약과 결과 검증으로 바꾼다. 자유로운 구현을 허용하면서도 어떤 정책을 만족해야 하는지 먼저 알려준다. 모든 대사를 자유 입력으로 자동 평가하는 시스템은 출시 필수 범위에 넣지 않는다.

## 분량 계획

| 콘텐츠 | 목표 수량 | 기본 경로에서의 사용 |
|---|---|---|
| 챕터 | 12 | 모든 경로에서 본편 완결 |
| 주 업무 | 96개 슬롯 | 조건부 장애는 예방 확인으로 대체 |
| 선택 사건 | 48 | 선택적으로 읽고 관계와 생활에 반영 |
| 회사 | 2 | 챕터 6의 도입과 공동 업무의 관점 차이 |
| 주요 인물 | 13 | 기존 동료 4명, 리크루터, 새 인물 8명 |
| 진로 결말 | 7 | 성과에 맞는 제안과 성장형 대안 제공 |
| 서비스 후일담 | 3 | 전환 완료, 단계 적용, 안전한 복귀 |
| 주요 무대 | 책상 공간 2종과 공통 앱 | 회사별 화면, 물건, 창밖과 소리로 변화 |

한국어 최종 대본은 공백을 포함해 20만~30만 자를 1차 예산으로 잡는다. 업무 정책, 코드 주석, UI 번역은 별도 관리한다. 분량을 맞추려고 대화를 늘리지 않고 플레이테스트에서 끊어 읽기와 반복 피로를 확인한 뒤 조정한다. 현재 기획 문서의 글자 수는 최종 게임 대본 분량이 아니다.

첫 플레이 30~45시간의 가정은 코딩·조사·계획 작업 24~35시간과 필수 대화·연출 6~10시간이다. 선택 사건 48개를 모두 읽으면 약 2.5~5시간이 추가되고, 다른 해결 방법 실험과 도구 탐색이 길어지면 총 45~60시간을 예상한다. 선택 사건 읽기만으로 플레이가 15시간 늘어난다는 식으로 계산하지 않는다.

챕터 2의 실제 측정으로 초보자와 숙련자의 시간 차이를 확인한다. 목표 시간을 맞추기 위해 고정 대기, 반복 커밋, 불필요한 로그 찾기를 늘리지 않는다. 숙련자가 빠르게 진행하는 것은 허용한다.

## 업무의 반복을 줄이는 원칙

같은 Git 명령을 입력하는 흐름은 첫 챕터에서 학습하고 이후에는 의미 있는 차이가 있을 때만 강조한다. 중반부터 이미 익힌 절차를 안내 카드 하나로 접고 키보드 작업을 계속할 수 있게 한다. UI 편의 기능과 실제 Git 사용 경로를 함께 제공한다.

챕터마다 플레이의 중심을 바꾼다. 재현, 상태 모델링, 설계 비교, 부하 분석, 이관, 리뷰, 조사, 범위 협상, 공동 운영, 인계가 차례로 전면에 나온다. 모든 업무가 새 함수 작성과 빨간 테스트 다섯 개로 끝나지 않게 한다.

새 기술을 소개할 때에는 한 번에 개념 하나와 예시 하나를 제시한다. 후반의 복합 사건은 앞에서 배운 계약을 조합한다. 실제 DB, 클라우드 계정, 외부 API 키가 있어야 이야기 진행이 되는 업무는 두지 않는다.

고객과 팀의 성과를 보여주는 평온한 완료 장면을 각 챕터에 최소 하나 둔다. 긴장 장면 직후에는 읽기와 판단을 쉬어 갈 여지를 주고, 다음 알림이 즉시 이전 성취를 덮지 않도록 한다.

## 콘텐츠 제작 형식

미션 정의에는 ID, 챕터, 서사 시점, 진입 조건, 목표, 관련 인물, 필요한 콘텐츠, 완료 증거, 장기 효과, 보완 경로, 저장 체크포인트를 둔다. 대사는 표시문과 저장 가능한 메시지를 구분하는 기존 `Game.L` / `Game.LL` / `Game.tx` 흐름과 연결한다.

장기적으로는 번역 문구와 미션 로직을 분리한다. 대본 원본과 생성된 콘텐츠 사이의 관계를 명확히 하고, 현재 `tools/gen_content.py`로 생성하는 파일을 사람이 직접 수정한 뒤 덮어쓰는 사고를 막는다. 생성기 변경 전에는 기존 한국어·영어 결과 차이를 검토한다.

선택 효과는 대사 안에 숨기지 않고 별도의 사건 결과로 기록한다. 같은 선택 이벤트가 두 번 도착해도 급여, 관계 변화, NPC 커밋, 고객 답장이 중복 실행되지 않게 한다. `await` 이후에도 해당 미션이 여전히 유효한지 확인하고 새 게임이나 언어 변경 중 이전 장면이 이어지지 않게 한다.

준비 단계의 업무를 먼저 끝냈다면 다시 타이핑을 요구하지 않고 현재 증거를 확인해 완료할 수 있게 한다. 업무가 시작되기 전에 만든 브랜치나 테스트를 무조건 무시하는 진행 판정을 피한다.

## 제작 순서

### 단계 1 챕터 2를 끝까지 만든다

시간 경과와 챕터 전환을 최소 범위로 추가하고, 챕터 2의 여덟 업무와 고객 답장까지 구현한다. 코드, 테스트, 힌트, 고객 표본, 한글·영문 UI를 같이 만든다. 기존 챕터 1 완료 세이브에서 새 챕터에 들어갈 수 있어야 한다.

완료 기준은 새 게임과 기존 완료 세이브에서 챕터 2의 도입과 결말까지 진행하고, 중간 업무의 저장·재개와 도움 경로가 모두 작동하는 것이다. 이 단계를 기준으로 업무당 실제 제작 시간과 플레이 시간을 측정한다.

### 단계 2 첫 성장 구간을 완성한다

챕터 3~5와 전환 면담, 채용 과정, ATLAS 초기를 구현한다. 장기 상태의 근거 기록과 보완 경로를 만든다. 이직 결정을 확정해도 캠페인이 조기에 종료되지 않도록 한다.

완료 기준은 초반 실수를 보완한 경로와 예방에 성공한 경로가 모두 챕터 5를 마치고, AI·페어링을 많이 사용한 플레이어도 다음 챕터에 진입하는 것이다.

### 단계 3 회사와 역할을 나눈다

챕터 6~9와 회사별 도입, 멘토링, AI 사건, 조직 개편을 구현한다. 두 회사의 공통 검증 계약을 재사용하고 대사와 담당 역할을 별도로 검토한다. 역할 경로 선택과 두 번째 이동 연결을 추가한다.

완료 기준은 소속과 직급이 달라도 필요한 권한과 증거를 얻을 수 있고, 주요 동료가 이동한 상태에서도 진행이 막히지 않는 것이다. 같은 사건을 다른 회사에서 플레이했을 때 담당 역할이 실제로 달라야 한다.

### 단계 4 결말까지 먼저 연결한다

챕터 10~12의 공동 계약, 전환, 인계, 진로와 후일담을 구현한다. 수치와 연출을 모두 완성하기 전에 전체 캠페인을 끝까지 플레이할 수 있게 한다. 모든 엔딩을 만든 뒤 초반 선택이 후반에 실제로 나타나는지 검토한다.

완료 기준은 두 회사와 두 역할의 기본 경로, 안전한 복귀 경로, 지원을 많이 받은 경로에서 본편이 완결되는 것이다. 나쁜 상황을 회복한 경로에도 후일담과 인정할 기여가 있어야 한다.

### 단계 5 출시 품질을 검증한다

전체 대본의 일관성, 읽기 속도, 언어별 화면, 입력 편의, 저장 복구와 실행 환경을 점검한다. 스토어 소개와 예고편은 실제 출시판이 제공하는 경로와 분량을 기준으로 작성한다. 문서에 계획된 기능을 이미 구현한 것처럼 광고하지 않는다.

완료 기준은 아래의 내부 출시 체크를 통과하는 것이다. 시나리오 기획 완료와 Steam 출시 준비 완료는 서로 다른 이정표로 관리한다.

- 처음 보는 사람이 고객과 동료의 역할을 구분하고 현재 해야 할 일을 설명할 수 있다.
- 챕터 1의 이름·쿠폰·로그인 정책과 후반의 계약이 서로 모순되지 않는다.
- 이직, 낮은 친밀도, 승진 지연, 도움 사용, 동료 이동, 되돌리기를 포함한 경로가 끝까지 연결된다.
- 모든 큰 결과에는 사전 정보와 확인 기회가 있으며, 불리한 상태를 회복할 수 있다.
- 예방에 성공한 플레이어에게도 충분한 마무리 장면과 고객 결과가 있다.
- 기술 전문가, 리드, 범위 유지, 휴식과 재학습 결말을 위계적으로 조롱하지 않는다.
- 개인 대화를 생략해도 주 업무의 정책과 필수 근거를 알 수 있다.
- 자동 진행 대화는 멈추거나 기록에서 다시 읽을 수 있고, 제한 시간 선택은 접근성 설정으로 완화할 수 있다.
- 한국어와 영어에서 선택 의미, 코드 정책과 인물 말투가 일치한다.

## 제품의 내부 출시 체크

실제 실행 환경의 격리와 런타임 동봉은 이야기 분량과 별도로 먼저 해결할 기술 작업이다. 현재 문서와 코드에는 OS 수준 격리가 미완료라고 명시돼 있으므로, 가상 경로를 표시하는 것을 안전한 코드 실행과 동일시하지 않는다.

- 깨끗한 Windows 사용자 환경에서 시스템 Git·Node 설치에 의존하지 않고 실행한다.
- 플레이어 테스트 코드가 허용된 작업 영역과 승인된 기능 안에서 실행되도록 제한한다.
- 무한 루프, 과다 출력, 프로세스 종료, 비정상 종료에서 UI가 복구되고 작업 결과가 일관된다.
- `content`의 TypeScript와 텍스트, 언어별 자료가 실제 배포 빌드에 포함된다.
- 저장 중 강제 종료, 잘못된 저장 파일, 이전 버전, Git 저장소와 상태 불일치에 복구 경로가 있다.
- 게임 재시작과 언어 변경이 NPC 변경·보상·대화 선택을 중복 실행하지 않는다.
- 모든 핵심 UI를 키보드로 사용할 수 있고, 글자 크기와 효과·소리 설정을 조정할 수 있다.
- 다른 경로와 이름의 Windows 계정에서도 실행하고, 사용자 실제 경로가 게임 메시지에 노출되지 않는지 확인한다.
- 릴리스 후보 빌드에서 본편 완료, 두 회사 경로, 중간 저장·재개와 엔딩을 확인한다.

실제 스토어 제출에 필요한 최신 항목, 배포 파일, 계정·결제 관련 절차는 제출 작업에서 공식 자료를 확인하고 별도로 점검한다. 이 문서에서는 검증하지 않은 스토어 요건이나 출시 일정을 확정하지 않는다.

## 범위가 커질 때 줄이는 순서

먼저 새 사무실 배경 수, 선택 사건의 개별 연출, 일회용 앱과 반복 대사를 줄인다. 두 회사의 공통 기술 업무를 공유하고 같은 역할의 조연을 통합한다. 번역과 세이브 검증을 마지막에 생략하지 않는다.

본편의 원인과 결과, 이직 후의 지속 진행, ATLAS의 결말과 다음 사람의 첫 PR은 유지한다. 미완성된 이야기 끝에서 후속 콘텐츠를 약속하는 방식으로 출시판의 끝을 대체하지 않는다. 실제 제작량이 목표를 크게 넘으면 챕터 2 측정 결과와 함께 업무 범위를 다시 설계한다.
