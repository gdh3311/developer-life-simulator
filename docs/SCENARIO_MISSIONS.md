# Developer Life Simulator 전체 업무와 사건

기획 버전 0.1 · 2026년 11월 23일

주 업무 96개를 실행 가능한 사건 단위로 나눈다. 챕터 1은 기존 10개 슬롯을 유지하고, 챕터 2~11은 각각 8개, 챕터 12는 6개로 구성한다. 조건부 장애 슬롯에는 예방 경로의 대체 업무를 넣어 성공한 플레이어도 동등한 이야기 장면을 얻는다.

각 업무는 고객 또는 동료의 구체적인 요청으로 시작하고, 게임 안에서 확인 가능한 산출물로 끝난다. 기술 수정이 없는 업무도 비교표, 인계 문서, 검토 의견처럼 남는 결과를 요구한다. 반복적인 브랜치 생성과 커밋은 중반부터 안내를 줄이고 일괄 작업을 허용한다.

업무 ID는 기획용이다. 기존 `d1_01`~`d4_10` ID를 즉시 교체하지 않는다. 각 챕터 안의 번호는 권장 진행 순서이며, 준비 업무는 안전한 범위에서 순서를 바꿀 수 있다. 각 사건의 장기 결과는 [인물과 선택의 후속 결과](SCENARIO_CHARACTERS.md)와 연결한다.

## 챕터 1 첫 출근

### C01 M01 내 자리가 생겼다

Alex의 환영 메시지와 Sophie의 안내로 시작한다. 채팅, 위키, 터미널을 열고 Git 작성자 정보를 설정한다. 인사말은 친밀도와 업무 성향만 조금 다르게 남고 정답을 두지 않는다. 마지막에 자신의 이름이 들어간 터미널 안내와 팀 채널의 환영 댓글이 남는다.

### C01 M02 오타 하나의 여정

Daniel이 README의 `Commerse` 오타 수정을 부탁한다. 플레이어는 브랜치, 수정, diff, 커밋, push, PR을 한 번 경험한다. PR 설명이 비어 있으면 거절보다 설명을 보충할 기회가 온다. 병합 뒤에는 자신이 바꾼 한 줄이 회사 저장소에 남고, 최초의 작은 성취를 연출한다.

### C01 M03 끝난 일의 뒷정리

병합 후 로컬 main을 갱신하고 작업 브랜치를 지운다. Sophie가 점심을 제안한다. 같이 먹기, 잠깐 마무리하고 합류하기, 오늘은 쉬고 다음 약속 잡기를 선택할 수 있다. 점심을 거절했다는 이유만으로 장기 관계가 나빠지지 않고, 첫날의 식사 장소와 대화 기록이 후속 장면의 소재가 된다.

### C01 M04 이름 없는 사용자

Mina가 프로필에 `undefined`가 표시되는 재현 테스트를 보낸다. 이름의 공백과 누락을 처리하고 회귀 테스트를 남긴다. Daniel의 추가 테스트 요청에는 동의하거나 다른 동등한 검증을 제시할 수 있다. 구현 방식은 자유이며 공개된 정책의 결과로 판정한다. Mina는 이후 플레이어에게 더 완성된 재현 자료를 보내게 된다.

### C01 M05 오후 네 시의 재발

Sophie의 닉네임 기능 이후 이름 버그가 다시 나타난다. Git 이력으로 변경을 찾되 닉네임 기능을 함께 유지해야 한다. 복구 후 대화에서는 따뜻하게 설명하기와 단호하게 절차 합의하기 모두 유효하다. Sophie의 실수는 Daniel이 최종 승인한 팀의 사건으로 다루고, 한 사람에게 모든 책임이 몰리지 않게 한다.

### C01 M06 처음 남기는 리뷰

쿠폰 PR의 계산과 정책을 비교한다. 문제 줄을 선택하고 정률 계산 또는 음수 결제 가능성을 근거로 의견을 남긴다. 정상 판단을 했다면 결함이 수정되고, 놓쳤다면 검증의 빈틈이 기록된다. 코드를 지적한 표현이 거칠면 기술 판단의 정당성과 별개로 대화 수습이 필요하다. 장기적으로 리뷰를 같이 하는 방식의 출발점이 된다.

### C01 M07 약속한 오후 세 시

배송비를 구현하는 사이 Daniel의 리팩터링과 충돌한다. 두 변경의 의도를 살려 병합하고 경계값을 검증한다. Alex에게 범위를 줄이기, 리뷰 시간을 요청하기, 데모를 샘플 데이터로 전환하기를 제안할 수 있다. 승인 우회는 실제 권한을 얻지 못하고 설명과 재합의를 거친다. 일정 합의가 챕터 2의 첫 업무 범위 논의에 다시 등장한다.

### C01 M08 로그인은 되는데 이유가 틀렸다

인증 서비스의 지연을 Monitor에서 확인한다. AICode의 패치는 타임아웃을 처리하지만 모든 실패를 같은 오류로 바꾼다. 직접 고치거나 AI 초안을 검토해 인증 실패와 공급자 오류를 구분한다. 실제 운영 권한을 가진 당직자가 배포와 종료 판단을 맡고 플레이어는 검증을 담당하도록 본편 대사를 보완한다. AI 사용 여부가 아니라 검증 기록이 남는다.

### C01 M09 쿠폰의 다음 날

리뷰에서 버그를 놓쳤다면 음수 결제 또는 잘못된 할인에 대한 핫픽스를 진행한다. 미리 잡았다면 Mina와 같은 주문 사례를 예방 테스트로 보존하고 판매자에게 정책 설명을 보낸다. 두 경로 모두 고객 영향과 재발 방지 기록을 산출한다. 예방 경로에 가상의 사고를 강제로 추가하지 않는다. 챕터 4의 기술 부채 논의에서 이 기록을 다시 볼 수 있다.

### C01 M10 첫 면담

회고에서 재발 방지책을 정하고 첫 달 평가와 다음 업무를 받는다. 사건을 사람 탓으로 정리하면 반박과 수정 기회를 준다. 본편의 정규직 전환은 챕터 3으로 이어지고, 기존 데모의 전환 결과는 선행 평가로 보존한다. Jamie의 연락은 공개 포트폴리오를 보고 보낸 커피챗 제안으로 바꾼다. 마지막에 달빛상점 지원 티켓이 배정된다.

## 챕터 2 내 이름이 적힌 업무

### C02 M01 월요일의 빈칸

달빛상점은 주문이 두 번 생겼다고 하지만 주문 번호 하나만 보냈다. 지원 티켓의 시간, 화면, 요청 식별자를 비교해 필요한 질문을 고른다. 무조건 고객에게 로그를 요구하는 대신 사내 기록으로 확인할 수 있는 범위를 먼저 찾는다. 산출물은 영향 범위가 적힌 재현 계획이며, 바로 수정하기와 자료를 기다리며 작은 실험하기 중 작업 순서를 정한다.

### C02 M02 재현되지 않습니다

개발 환경에서는 주문이 한 번만 생긴다. 응답 지연과 같은 요청 재전송을 조합한 테스트를 만든다. 사용자의 연속 클릭과 서버 재시도가 겹친다는 사실이 드러난다. 버튼만 막는 빠른 완화와 서버 중복 방지의 범위를 나눠 제안한다. 결과는 두 종류의 재현 테스트이며, 빠른 완화를 먼저 내면 고객의 불편이 먼저 줄어든다.

### C02 M03 같은 요청 두 번

동일한 요청 키와 동일 내용에는 같은 주문을 반환하고, 같은 키에 다른 내용이 오면 충돌을 반환하는 작은 모듈을 만든다. 테스트용 저장소와 순차 요청만 다루며 동시성은 아직 해결했다고 주장할 수 없다. 현재 계약을 명시하면 Daniel은 작은 변경을 승인한다. 모든 경우를 한 번에 해결하려 하면 일정 재합의 장면이 열린다.

### C02 M04 남겨야 할 로그

Mina는 이름과 주소가 포함된 디버그 로그를 발견한다. 주문 흐름을 추적할 요청 ID와 결과 코드만 남기고 민감한 필드를 제거한다. 과도하게 지워 재현이 어려워지면 필요한 맥락을 다시 추가한다. 산출물은 로그 예시와 삭제 확인 테스트다. 이 기준이 챕터 8의 조사 도구에 재사용된다.

### C02 M05 기다리는 사람의 화면

Sophie와 버튼 상태와 오류 응답을 맞춘다. 프론트엔드의 임시 주문 ID와 서버의 확정 ID가 혼동되고 있었다. API 예시를 함께 고치고 두 사람이 합의한 상태 전이표를 만든다. 백엔드가 먼저 다 정한 뒤 넘기면 수정은 빠르지만 합의 누락이 남고, 짧은 페어링은 현재 시간을 쓰는 대신 후속 지원을 줄인다.

### C02 M06 버튼 바깥의 중복

시뮬레이션 작업자 두 개가 동시에 들어오면 순차 테스트에서 만든 중복 방지가 깨진다. 원자적으로 키를 선점하는 테스트용 저장소 인터페이스를 사용하고 실패한 생성은 재시도 가능하게 정리한다. 실제 DB를 설치하거나 운영 서버를 연결하지 않는다. 산출물은 동시 요청과 생성 실패 복구 테스트다. 챕터 5의 재고 예약과 챕터 11의 재전송 문제에 이어진다.

### C02 M07 고쳤다는 말의 조건

수정판을 달빛상점에 제한 적용한다. 적용 전후의 중복 건수와 요청량을 같이 비교하고, 줄어든 주문량을 성공으로 오해하지 않도록 한다. 더 관찰하기, 적용 범위를 확대하기, 이전 버전으로 되돌리기를 증거에 맞춰 선택한다. 산출물은 배포 확인 기록과 다음 확인 시점이다. 명확한 종료 기준을 세우면 운영자가 일을 이어받을 수 있다.

### C02 M08 저녁 여섯 시의 답장

고객에게 원인과 적용 범위, 남은 제약을 설명하고 지원 티켓을 닫는다. 윤서진이 매일 주문을 손으로 합치던 시간이 줄었다고 답한다. Daniel과 Mina에게 공을 나누거나 자신의 성과만 적을 수 있으나 실제 기여 기록과 함께 후속 대화가 진행된다. 마지막 감사 로그에서 두 종류의 옛 주문 식별자가 발견되고, `LEGACY-17` 조사 티켓이 만들어진다.

## 챕터 3 처음부터 끝까지

### C03 M01 출시일이 먼저 정해졌다

Alex가 예약 판매 기능의 출시일과 판매자 문구를 가져온다. 플레이어는 사용 사례를 읽고 포함할 기능과 미룰 기능을 명시한다. 원하는 모든 항목을 받아들이면 지원 인력이나 기간을 늘리는 협상이 반드시 뒤따른다. 산출물은 확인 가능한 수용 조건이며, 고객이 약속을 다르게 이해하는 후속 장면을 예방할 수 있다.

### C03 M02 같은 시각 다른 날짜

판매자의 마감 시각과 서버 시간대가 다르다. UTC 기준 저장과 판매자 현지 표시의 경계를 정하고 마감 직전·정각·직후를 테스트한다. Sophie가 제안한 문구가 코드를 단순하게 만들 수 있다. 산출물은 날짜 처리 함수와 표시 규칙이다. 챕터 10의 국제 정산에서 같은 경계가 다시 필요해진다.

### C03 M03 취소 버튼의 두 번째 의미

결제 전 취소와 결제 후 환불 요청을 같은 상태로 저장하던 코드를 분리한다. 이미 배송 준비에 들어간 주문의 처리도 표로 정한다. 정책이 없으면 임의로 정답을 넣지 않고 Alex와 판매자에게 질문한다. 산출물은 주문 상태 전이와 테스트이며, 이후 환불 기록 이관의 기반이 된다.

### C03 M04 아주 작은 베타

고객 세 곳 중 서로 다른 사용 패턴을 가진 한 곳을 골라 제한 출시한다. 가장 친한 고객만 고르면 빠르게 피드백을 얻지만 드러나지 않는 사용 방식이 있다. 두 번째 검증군을 추가할 수 있다. 산출물은 베타 대상 선정 이유와 기능 플래그 계획이다. 기능 플래그는 운영 시뮬레이션 UI에서 적용한다.

### C03 M05 테스트는 통과했는데요

Mina가 실제 화면에서 혼란을 발견한다. 기술 규칙은 맞지만 구매자는 배송 예정일을 수령일로 읽는다. 구현을 바꾸거나 표시와 안내를 바꿔 혼란을 해결한다. 산출물은 수정된 예시와 지원 문서다. 사용자 오해를 무조건 사용자 탓으로 돌리면 동일 문의가 다음 업무에 남는다.

### C03 M06 첫 출시 공지

릴리스 노트와 되돌리기 조건을 정리하고 정식 출시한다. 배포 버튼을 누르는 장면보다 출시 후 확인 대상을 고르는 작업에 비중을 둔다. 지표와 고객 문의가 기준 안에 있으면 평온하게 끝난다. 산출물은 공지와 출시 체크 기록이며, 첫 공개 성과가 Connectly 포트폴리오에 들어간다.

### C03 M07 다음 주에도 내 일

기능 출시 후 담당자와 문의 대응 시간을 정한다. 개발이 끝났다는 이유로 소유자를 비워 두면 반복 문의가 개인 메시지로 쌓인다. 업무 시간을 정하고 공용 채널로 옮기는 방식으로 회복할 수 있다. 산출물은 담당 범위와 운영 설명서다. 챕터 7에서 지우에게 넘길 첫 문서가 된다.

### C03 M08 첫 번째 계약서

정규직 전환 면담과 Brightloop 커피챗을 진행한다. 면담에서는 코드, 협업, 고객 결과의 실제 기록을 고른다. 부족한 부분이 있으면 기간과 지원이 정해진 개선 계획을 받고 본편은 계속된다. Jamie와는 원하는 업무를 합의하며, 정식 이직 결정은 챕터 5 이후다. 산출물은 개인 성장 계획과 다음 평가일이다.

## 챕터 4 오래된 결정

### C04 M01 지울 수 없는 조건문

AI 변경 자동화의 시범 업무로 반복적인 변환 코드를 고른다. 실제로 시간을 절약하고 테스트도 통과한다. 산출물은 채택 기준과 검토 시간 기록이다. AI를 사용하지 않아도 공통 검토 기준을 만들며, 사용 여부를 도덕 선택으로 다루지 않는다.

### C08 M02 같은 대답을 하는 테스트

생성 코드와 생성 테스트가 같은 잘못된 가정을 공유한다. 외부 정책 예시와 과거 고객 사례를 독립적인 기준으로 추가한다. 산출물은 기존 테스트와 독립된 계약 테스트다. 이미 관련 기록을 남겼다면 그 자료를 재사용하고 반복 설명을 줄인다.

### C08 M03 다른 판매자의 문구

Mina가 판매자 A의 화면에 B의 문구가 잠깐 나타난 표본을 보낸다. 로그 최소화 기준을 지키며 캐시 경계를 재현한다. 산출물은 판매자 구분이 누락된 캐시 키 테스트다. 조사 시간에는 기능을 제한할 수 있으며 완전한 원인을 찾을 때까지 노출을 계속할 필요가 없다.

### C08 M04 어디까지 보였나요

보안 담당 오나경과 영향 범위를 분류한다. 확인된 노출, 가능성만 있는 구간, 확인할 수 없는 구간을 구분한다. 산출물은 근거와 불확실성이 분리된 조사표다. 기록이 부족하면 부족한 상태로 대응 계획을 세우며 그 빈칸을 확실한 숫자로 꾸밀 수 없다.

### C08 M05 오늘 고칠 것 내일 고칠 것

최소 캐시 수정과 전체 키 체계 개편 중 작업 순서를 정한다. 고객 영향 제한, 회귀 테스트, 점진 확대를 묶는다. 산출물은 복구 패치와 장기 개선 이슈다. 큰 변경 하나로 모든 문제를 해결하는 것보다 현재 영향과 이후 유지보수를 따로 검증한다.

### C08 M06 고객에게 설명하는 문장

지원 담당 배유리가 보낼 공지를 검토한다. 확인된 사실과 조치, 추가 업데이트 시간을 명시한다. 실제 법률 절차는 게임의 업무 규칙으로 단순화하고 특정 국가의 법적 의무를 정답으로 출제하지 않는다. 산출물은 내부 승인된 모의 공지다. 숨기려는 선택에는 반대와 수정 기회가 먼저 온다.

### C08 M07 줄어든 시간은 누구의 시간

유진의 요청으로 Alex가 보낸 축약 보고서에서 검토 시간에 대한 조건이 빠지고 작성 시간만 성과로 사용된다. 검토, 운영, 재처리까지 포함한 지표를 제시하거나 현재 지표의 한계를 공식 부록에 남긴다. 산출물은 수정된 시범 결과와 조정할 약속 목록이다. 근거를 반복해서 무시하면 후반에 인력 배치가 틀어질 수 있으나 플레이어가 확인할 전조를 제공한다. Alex의 사과 뒤에는 실제 고객 범위 조정이 있어야 신뢰가 회복된다.

### C08 M08 계속 쓸 도구

자동화 대상과 승인 책임, 중단 기준을 팀과 합의한다. 전면 허용, 제한 사용, 해당 영역 사용 중단을 범위별로 나눌 수 있다. 산출물은 채택 정책과 실제 사례다. 나경은 기록이 좋은 플레이어에게 후반 공동 전환의 보안 검토를 맡긴다.

## 챕터 9 이름이 바뀐 팀

### C09 M01 바뀐 조직도

조직 개편 공지가 오고 담당 팀 이름이 달라진다. 업무 목록에서 새 담당자가 없는 항목을 찾는다. 산출물은 소유권 공백 목록이다. 개인의 불안을 긴 대사로 설명하기보다 알림 수신자와 승인 버튼의 변화로 보여준다.

### C09 M02 다 할 수 없다는 표

새 조직이 이전 약속을 모두 유지하려 한다. 실제 가용 시간과 운영 부담을 비교해 중단할 업무를 제안한다. 산출물은 유지·축소·종료 계획이다. 부풀린 자동화 성과가 있다면 이번 계획에서 보정할 기회가 있으며, 과거 오류를 인정해도 협상은 계속된다.

### C09 M03 종료 버튼이 없는 기능

사용량이 적은 예약 판매 부가 기능을 종료할지 유지할지 검토한다. 소수의 핵심 사용자를 확인하고 대체 경로와 공지 기간을 정한다. 산출물은 폐기 또는 제한 유지 계획이다. 챕터 3의 고객 기록이 있으면 숫자 뒤에 남은 사용자를 쉽게 찾는다.

### C09 M04 Daniel의 다음 자리

Daniel이 관리, 기술 전문, 휴식 중 고민을 이야기한다. 플레이어는 그를 붙잡기보다 병목과 원하는 일을 구분하도록 대화를 돕는다. 산출물은 본인이 동의한 담당 재배치다. 관계가 낮으면 개인적인 설명은 줄어들어도 업무 인수인계는 가능하다.

### C09 M05 마지막 근무일

동료 한 명이 이동 또는 퇴사를 결정한다. 비밀 권한을 넘겨받는 대신 정상적인 접근 회수와 기록 이전을 진행한다. 산출물은 실제로 따라 할 수 있는 인수인계다. 떠나는 동료의 사정은 플레이어가 선택한 회사에 따라 바뀌며, 모두를 남기는 완벽한 결말은 두지 않는다.

### C09 M06 남은 사람의 월요일

알림이 남은 사람에게 몰린다. 소유권과 알림 규칙을 고쳐 실제 담당자에게 연결하고 불필요한 호출을 줄인다. 산출물은 조정된 운영 분담표다. 혼자 감당하는 선택에도 조직 지원을 요청할 회복 경로를 남긴다.

### C09 M07 다시 온 연락

예전에 오퍼를 보류했거나 회사 이동을 원하는 플레이어에게 제한된 이동 창이 열린다. 경력과 진행 중 프로젝트에 맞는 직무를 면담한다. 산출물은 이동 또는 잔류의 재합의다. 두 번째 이동을 해도 챕터 10 공동 프로젝트에서 반대편 역할을 맡아 본편에 합류한다.

### C09 M08 달라진 이름표

새 팀의 첫 운영 주기를 점검한다. 종료한 업무가 정말 종료됐는지, 새 담당자가 승인할 수 있는지 확인한다. 산출물은 팀의 다음 분기 계획이다. 이 장면 뒤에는 잠깐 평온한 시간이 흐르고 공동 프로젝트 제안이 온다.

## 챕터 10 두 회사가 쓰는 기록

### C10 M01 같은 계약의 양쪽

모자이크 마켓 공동 계약의 범위와 두 회사의 역할을 정한다. 플레이어는 자신의 회사가 편한 방식만 주장할 수 있지만 상대의 제약도 확인해야 완료된다. 산출물은 공동 수용 조건이다. 친분이 없어도 공식 협의 문서로 모든 필수 정보를 얻는다.

### C10 M02 원인가 센트인가

돈의 단위와 통화별 자릿수를 명시하는 변환 계층을 만든다. 부동소수점 덧셈과 정수 단위의 차이를 작은 예시로 확인한다. 산출물은 통화가 붙은 금액 타입과 테스트다. 초반에 환불 반올림을 정리한 자료가 있으면 맥락을 빠르게 이해한다.

### C10 M03 어제 환불된 오늘 주문

두 시간대의 이벤트가 날짜 순으로 정렬돼 상태가 틀어진다. 이벤트 시각과 수신 시각을 분리하고 상태 규칙을 적용한다. 산출물은 순서가 바뀐 이벤트의 재생 테스트다. 정렬 한 줄로 모든 문제를 해결할 수 없다는 것을 확인한다.

### C10 M04 소유하지 않는 데이터

두 회사가 전달할 데이터의 최소 항목과 보관 구간을 합의한다. 지원에 필요하다는 이유로 모든 필드를 받는 대신 목적별로 나눈다. 산출물은 승인된 교환 스키마와 모의 삭제 확인이다. 챕터 8의 사건이 있었다면 그 교훈을 실제 계약에 반영할 수 있다.

### C10 M05 중간에 멈추는 연습

부분 이관 후 중단하는 훈련을 한다. 새 시스템에 들어온 변경을 구분해 이전 시스템으로 조정하는 순서를 검증한다. 산출물은 되돌리기 훈련 결과다. 되돌릴 수 없는 구간은 명시적으로 선언하고 그 앞에서 별도의 승인 기준을 둔다.

### C10 M06 누구의 새벽인가

회사와 고객의 시간대가 달라 작업 시간을 협의한다. 업무 시간 내 제한 전환, 유급 교대, 고객별 분할 중 현실적인 계획을 고른다. 산출물은 지원 가능한 작업창과 교대표다. 가장 희생적인 선택이 자동으로 관계 보상을 받지 않는다.

### C10 M07 계약서보다 작은 약속

옛 동료와 위험 하나를 함께 검토한다. 개인 채팅에서 얻은 설명을 공동 문서로 옮겨 다른 담당자도 볼 수 있게 한다. 산출물은 공동 운영 설명서다. 높은 친밀도는 추가 대사와 빠른 이해를 제공하지만 운영 권한을 우회하지 않는다.

### C10 M08 이름을 함께 적는다

정식 전환 준비 검토를 진행한다. 남은 위험에 담당자, 기준, 확인 시점을 붙인다. 산출물은 양측이 확인한 준비 상태다. 선택한 보완 범위에 따라 챕터 11에서 쓸 도구와 자동 판정이 늘어나며, 과장된 완료 선언은 이후 추가 확인 업무로 돌아온다.

## 챕터 11 금요일 전환

### C11 M01 전환해도 되는 금요일

행사 일정과 정산 주기를 보고 실제 가능한 작업창을 확인한다. 금요일이라는 이름만으로 판정하지 않고 지원 인력, 고객 영향, 복구 가능 시간을 확인한다. 산출물은 진행·축소·연기의 근거다. 연기하면 고객 비용과 새 지원 일정을 협의한 후 동일 전환에 다시 진입한다.

### C11 M02 첫 번째 판매자

작은 집합부터 전환하고 비교 결과를 확인한다. 준비가 좋으면 정상 대조가 자동으로 진행된다. 산출물은 첫 단계 전환 결과다. 모든 검사를 수동으로 반복하게 하지 않고 자신이 만든 도구가 일을 덜어 주는 보상을 준다.

### C11 M03 늦게 도착한 옛 주문

이전부터 경고됐던 장기 미결제 주문의 이벤트가 들어온다. 멱등성과 별칭 매핑을 확인한다. 준비된 테스트가 있으면 자동 격리되고 없으면 영향 범위를 제한해 수동 대조한다. 산출물은 중복 없는 재생 결과와 예외 목록이다. 초반 주문 키가 같은 화면에서 다시 등장한다.

### C11 M04 모두가 다른 창을 본다

지원, 운영, 개발이 다른 수치를 보고 있다. 플레이어는 공통 기준 시각과 진행 상태를 맞춘다. 산출물은 한 장의 공동 상황 기록이다. 팀 리드 경로에서는 작업 배분을, 기술 경로에서는 차이를 설명하는 대조 도구를 중심으로 플레이한다.

### C11 M05 계속할지 돌아갈지

검증된 중단 기준과 현재 상태를 비교한다. 계속 진행, 대상 축소, 되돌리기 중 선택한다. 조건을 충족하면 어느 선택도 성공 경로가 될 수 있으며, 되돌렸다는 이유로 무능 엔딩을 주지 않는다. 산출물은 판단 근거와 다음 실행 계획이다.

### C11 M06 맡겨야 끝나는 일

지우 또는 대체 담당자에게 독립적인 확인 작업을 맡긴다. 이전 멘토링이 부족하면 범위를 줄이고 체크리스트를 함께 읽는다. 산출물은 다른 사람이 완료한 검증이다. 관계가 끊겼거나 인물이 이동했다면 동일 권한의 다른 담당자가 참여해 필수 진행을 보장한다.

### C11 M07 다음 교대자에게

미해결 항목과 고객별 상태, 되돌리기 가능 구간을 정리한다. 혼자 남아 끝내려 하면 교대 계획과 컨디션을 다시 협의한다. 산출물은 실제 다음 담당자가 확인한 인계다. 플레이어가 자리를 떠나도 시뮬레이션 시간과 서비스 그래프가 계속 움직인다.

### C11 M08 끝났다고 말할 때

전환 완료 또는 제한 복귀를 선언하고 후속 대조 일정을 확정한다. 고객 영향이 남았다면 종료 보고에서 삭제할 수 없다. 산출물은 완료 기록과 다음 확인 담당이다. 대형 사고를 피한 경로는 조용한 축하와 평범한 퇴근으로 결말을 맞고, 수습 경로는 같은 분량의 지원과 회복 장면을 얻는다.

ATLAS 전환 뒤의 실제 고객 결과를 확인한다. 남은 재처리, 환불 보정, 또는 정상 확인을 진행한다. 산출물은 고객별 종료 상태다. 마지막 보고서를 좋게 쓰는 것보다 누구의 일이 아직 남아 있는지 확인하는 것이 완료 조건이다.

### C12 M02 마지막 호환 코드

`LEGACY-17`을 사용하는 고객이 남았는지 확인한다. 모두 이관됐으면 코드를 안전하게 제거하고, 남아 있으면 유지 담당과 종료 조건을 정한다. 산출물은 삭제 PR 또는 관리 계획이다. 모든 옛 코드를 지우는 것이 유일한 성공이 되지 않는다.

### C12 M03 나 없이 하는 연습

다음 담당자가 운영 문서만 보고 작은 요청을 처리한다. 플레이어는 실제로 개입을 줄이고 막힌 지점을 기록한다. 산출물은 검증된 인계와 수정된 문서다. 전임자가 모든 답을 기억하는 것보다 다음 사람이 찾을 수 있게 만드는 과정이 마지막 기술 업무다.

### C12 M04 네 번째 해의 면담

성과와 생활, 앞으로 맡고 싶은 일을 정리한다. 기술 전문, 팀 리드, 이동, 휴식, 작은 제품에 대한 제안을 비교한다. 부족한 조건은 무엇인지 공개하고 지금 선택할 수 있는 대안을 함께 제시한다. 산출물은 플레이어의 다음 역할과 조정할 업무다.

### C12 M05 이름을 고치는 사람

새 동료가 README 오타 수정 PR을 올린다. 플레이어는 근거를 주는 리뷰, 함께 읽는 리뷰, 이미 잘한 점을 먼저 짚는 리뷰 중 자신의 방식으로 답한다. 산출물은 새 사람이 직접 마무리한 첫 PR이다. 첫날의 UI와 효과음을 짧게 반복하고 인물의 성장을 화면으로 보여준다.

### C12 M06 오늘은 여기까지

남은 메시지를 읽고 책상 물건과 개인 기록을 정리한다. 선택한 진로에 맞춰 자리 이동, 퇴근, 휴식 시작 또는 작은 제품의 첫 업무가 보인다. 산출물은 다음 담당자와 자신의 일정이다. 커리어, 서비스, 관계, 생활의 후일담이 각각 이어지고 본편은 완결된다.
