챕터 제목은 **내 이름이 적힌 업무**다. 첫 달의 평가를 지나 2개월 차가 된 플레이어가 처음으로 고객 티켓의 담당자가 된다. 달빛상점의 중복 주문을 해결하는 동안 재현, 범위 합의, 동료와의 인터페이스 협의, 검증, 고객 설명을 경험한다.

기본 플레이 2~3시간을 목표로 한다. 중요한 근무일 세 번을 선택해 보여주며 사이의 날짜는 생략한다. 미션의 어려움은 새로운 명령의 양보다 무엇을 확인해야 하는지에서 나온다. 후반에도 작은 함수와 준비된 테스트 환경으로 해결 가능해야 한다.

현재 챕터 1의 사건 상태를 읽어 대사 일부를 바꾸지만, 버그를 놓친 플레이어도 필요한 지식을 배우고 들어올 수 있다. 과거 테스트를 그대로 복사해야 통과하는 조건은 두지 않는다. 첫 챕터에서 정규직 전환된 기존 세이브는 해당 사실을 인정하는 도입 문장을 사용한다.

## 시작 전 상태와 연출

새 월요일이다. 방의 기본 구조는 같지만 책상 옆에 지난달 급여 안내와 작은 달력이 생겼다. 구매한 물건은 그대로 남는다. 메신저에는 주말 메시지 여러 개가 보이지만 읽지 않은 것 때문에 감점을 주지 않는다.

작은 시간 경과 카드에 “두 번째 달 · 월요일”을 표시한다. 기존의 `DAY 5` 같은 실행 인덱스와 서사의 달을 분리한다. 플레이어의 실제 이름은 모든 대본에서 `{player}`로 치환한다.

팀 채널 상단에는 “이번 주 지원 담당: {player} / 검토: Daniel / 고객 창구: Yuri”가 고정돼 있다. 플레이어가 혼자 운영 책임을 떠맡은 것처럼 보이지 않게 검토자와 배포 담당자를 명시한다.

## C02 M01 월요일의 빈칸

### 발단

TaskBoard에 `NXR-021 주문이 두 번 들어왔어요`가 생긴다. 보고자는 Yuri이고 고객은 달빛상점이다. 첨부된 고객 메시지는 아래와 같다.

**윤서진:** “어제 저녁에 같은 분 주문이 두 개 들어왔는데요. 결제는 하나 같기도 하고요. 어제는 바빠서 하나 지우고 보냈어요. 오늘도 그러면 곤란해서 연락드려요.”

티켓에는 주문 번호 하나, 화면 캡처, 대략적인 시각만 있다. 개발자가 바로 코드를 수정할 정보는 부족하다. 상점 대표가 잘못 기록했다는 대사로 시작하지 않는다.

### 플레이

Monitor의 준비된 표본과 지원 기록을 비교해 고객에게 추가로 물을 항목을 고른다. 필요한 정보는 발생 시각의 범위, 같은 구매 시도인지, 보이는 주문 번호, 결제 상태다. 카드 세 개를 고르는 간단한 조사 UI를 사용하고 터미널로 같은 표본을 읽는 경로도 둔다.

개인 주소와 구매자 이름은 필요하지 않다. 불필요한 항목을 골랐다면 Yuri가 이유를 묻고 다시 고르게 한다. 테스트용 식별자만 들어 있는 표본을 게임에 포함한다.

### 대화

**Yuri:** “고객에게 다시 물어볼 수 있어요. 다만 바쁜 시간에는 답이 늦을 거예요. 우리가 볼 수 있는 것부터 정리해 줄래요?”

**선택 A:** “지금 기록으로 범위를 좁히고 주문 번호만 더 부탁드릴게요.”

**Yuri:** “좋아요. 고객이 왜 필요한지 알 수 있게 한 문장만 붙여 주세요.”

**선택 B:** “코드부터 볼게요. 문의는 답이 올 때까지 열어 둘게요.”

**Daniel:** “가능해요. 다만 어떤 상황을 찾는지 먼저 적어 놓으세요. 비슷해 보이는 다른 버그를 고칠 수도 있으니까요.”

**선택 C:** “제가 고객에게 직접 물어봐도 될까요?”

**Yuri:** “같이 답장을 쓰죠. 처음에는 제가 보내고, 다음부터는 담당 범위를 맞춰 봐요.”

### 완료와 복구

완료 조건은 재현 계획 카드에 현재 확인된 사실, 아직 모르는 것, 다음 확인 행동이 채워지는 것이다. 특정 질문 조합을 암기해야 하는 퍼즐로 만들지 않는다. 정보가 충분하면 여러 조사 순서가 통과한다.

완료 후 두 주문이 700밀리초 간격으로 생겼고 같은 결제 참조를 가리킨다는 표본을 얻는다. 고객 답변이 늦으면 같은 사실을 지원 기록에서 확인할 수 있다. 기다림으로 게임 진행이 멈추지 않는다.

## C02 M02 재현되지 않습니다

### 플레이

`tests/order_request.test.ts`의 짧은 예시를 바탕으로 지연 응답과 같은 요청 재전송을 재현한다. 준비된 가짜 시계와 요청 도우미를 사용한다. 실제 네트워크, 실제 결제 서비스, 외부 계정은 필요하지 않다.

먼저 순차 재시도로 중복을 확인한다. 버튼 연속 클릭은 Sophie가 담당하는 화면 완화의 근거이며 서버 수정의 대체가 아니다. 이 시점에는 동시 요청 재현을 요구하지 않고, 나중에 범위를 넓힐 단서를 남긴다.

### 대화

**Sophie:** “버튼 누르면 바로 비활성화할게요. 그럼 두 번은 못 누르잖아요.”

**Mina:** “화면에서는요. 중간에 요청이 다시 가면 어떻게 되죠?”

**Sophie:** “아, 응답이 안 와서 다시 보내는 경우요?”

**Daniel:** “두 수정이 다른 문제를 막는 거예요. 둘 다 작게 할 수 있겠네요.”

**선택 A:** “화면 완화를 먼저 내고 서버 수정 범위를 바로 잡죠.”

**Alex:** “먼저 줄어드는 불편과 남는 위험을 고객에게 나눠서 설명할게요.”

**선택 B:** “서버 재현부터 확정하고 한 번에 안내하겠습니다.”

### 완료와 복구

같은 요청이 두 주문을 만드는 실패 테스트와 정상 단일 요청 테스트가 있으면 완료된다. 테스트를 쓰기 어렵다면 Mina의 최소 재현을 받아 의도와 실제 결과를 비교하는 방식으로 진행한다. 도움을 받아도 동일한 오류 근거가 기록된다.

## C02 M03 같은 요청 두 번

### 발단

Wiki에 새 정책 초안이 올라온다. 정의가 짧고 예제가 함께 있다. 플레이어는 코드를 고치기 전에 같은 키에 다른 내용이 온 경우를 질문할 수 있다.

### 정책과 입력

테스트용 주문 모듈은 `createOrder(request, store)`로 표현한다. 요청은 `shopId`, `requestKey`, `items`를 가진다. 같은 상점과 같은 키로 같은 항목을 다시 보내면 처음 만든 주문을 반환한다. 같은 키인데 항목이 다르면 `REQUEST_CONFLICT`를 반환한다. 상점이 다르면 같은 키를 써도 별개 요청이다. 키가 비어 있으면 `REQUEST_KEY_REQUIRED`를 반환한다.

키의 무한 저장과 실제 운영 기간 정책은 이번 작은 모듈의 범위 밖이다. 도입 대사와 문서에 명시하고 챕터 5에서 만료와 재처리 범위를 확장한다. 표본의 항목 순서는 정규화된 입력으로 제공한다. 직렬화 순서 차이를 숨겨진 함정으로 출제하지 않는다.

### 대화

**플레이어가 정책의 빈칸을 묻는 경우:** “같은 키인데 상품이 바뀌면 새 주문으로 봐야 하나요?”

**Alex:** “고객 입장에서는 새 주문일 수도 있는데, 실수일 수도 있겠네요.”

**Mina:** “같은 키로 조용히 다른 주문이 생기면 추적이 안 돼요. 다른 키로 다시 요청하도록 구분하면 어떨까요?”

**Daniel:** “그 규칙을 API 예시에 같이 적죠.”

**플레이어가 질문 없이 구현한 경우:** 같은 규칙이 공개 테스트의 예제로 먼저 나타난다. 모르는 정책을 맞혀야 하는 구조는 두지 않는다.

### 완료와 복구

정상 생성, 동일 재시도, 내용 충돌, 상점 분리, 빈 키의 공개 계약 테스트를 통과한다. 서버의 순차 처리까지만 다룬다는 제약을 PR에 남긴다. 이 시점에서 전체 문제가 해결됐다는 임무 완료 알림은 띄우지 않는다.

Daniel이 “좋아요. 순서대로 들어오면 맞네요. 실제로 겹치면 어떨지는 다음 확인에서 봅시다”라고 답해 C02 M06을 예고한다. 플레이어가 먼저 동시성을 검증했다면 해당 업무는 새 구현 대신 검증 설명과 실패 복구를 다룬다.

## C02 M04 남겨야 할 로그

### 발단

디버그 출력에 테스트 구매자의 주소와 이름이 보인다. 모두 가상 데이터이며 실제 사용자 정보는 없다. Mina는 문제를 찾는 데 필요했던 정보가 무엇인지 묻는다.

**Mina:** “이 로그는 주문 찾기에는 편한데, 주소까지 있어야 했나요?”

**선택 A:** “요청 ID와 결과 코드만 남기겠습니다.”

**Mina:** “어느 상점의 요청인지와 재시도 여부도 필요하겠네요. 최소한으로 추적은 돼야 해요.”

**선택 B:** “이름을 지우면 문의랑 연결하기 어려울 것 같아요.”

**Yuri:** “지원 도구에서는 권한 있는 사람이 주문 번호로 볼 수 있어요. 로그에 한 벌 더 없어도 돼요.”

**선택 C:** “일단 전부 지우고 필요하면 다시 넣죠.”

**Daniel:** “다음에도 똑같이 막힐 수 있어요. 이번 재현에 쓴 필드를 같이 골라 봅시다.”

### 플레이

로그 출력 함수에서 `requestId`, 가상 상점 ID, 결과 코드, 재시도 여부, 처리 시간을 남긴다. 결제 토큰과 구매자 필드는 포함하지 않는다. 준비된 로그 예시에서 허용 필드와 불필요한 필드를 고른 뒤 함수와 테스트를 수정한다.

### 완료와 복구

재시도 흐름을 추적할 수 있고 구매자 필드가 남지 않는 테스트를 통과한다. 남기는 항목의 이름이 예시와 정확히 같아야 할 필요는 없다. 외부 계약에 필요한 정보와 제외 대상의 동작으로 판정한다.

완료하면 Mina는 “그럼 다음에 이 로그를 보는 사람이 저 아니어도 찾겠네요”라고 한다. 조사 자료를 안전하게 남기는 원칙이 장기 상태에 기록된다. 이 장면에서 직무 교육이나 처벌성 경고창을 길게 띄우지 않는다.

## C02 M05 기다리는 사람의 화면

### 발단

Sophie가 “실패했다고 나왔는데 주문이 있으면 화면은 뭘 보여줘야 해요?”라고 묻는다. 기술적으로 성공한 서버와 실패처럼 보이는 화면 사이의 틈이 드러난다.

### 화면 상태 합의

| 상태 | 화면 | 서버와의 약속 |
|---|---|---|
| 요청 전 | 주문 버튼 사용 가능 | 새 요청 키 준비 |
| 응답 대기 | 처리 중 표시 | 같은 시도에는 같은 키 유지 |
| 결과를 아직 모름 | 확인 중 표시와 확인 동작 | 같은 키로 결과 확인 또는 재시도 |
| 주문 확정 | 기존 주문 번호 표시 | 같은 키에 같은 결과 반환 |
| 내용 충돌 | 주문 내용 재확인 안내 | 새 시도에서 새 키 사용 |

이 표는 게임 속 합의 문서로 남긴다. 플레이어가 프론트엔드 전체를 다시 구현하지 않는다. 필요한 응답 예시와 작은 표시 함수만 수정하거나 Sophie가 수정한 PR을 검토한다.

### 대화

**Sophie:** “실패라고 쓰면 고객은 버튼을 다시 누를 거예요. 그런데 실패가 아니라 아직 모르는 거잖아요.”

**플레이어 선택 A:** “맞아요. 결과를 모르는 상태를 분리하죠.”

**플레이어 선택 B:** “응답 종류를 더 늘리면 복잡해질 것 같아요. 기존 상태로 설명할 수 있을까요?”

**Sophie:** “그럼 예시를 두 개만 놓고 볼까요? 실패한 경우랑 주문은 생겼는데 답을 못 받은 경우요.”

B도 검증 결과에 따라 단순한 표현으로 합의할 수 있다. 새 상태 이름을 반드시 추가해야 한다는 구현 강요는 하지 않는다. 사용자에게 거짓 실패를 보여주지 않는 결과가 기준이다.

### 완료와 복구

확정 주문의 재시도, 불확실한 응답, 내용 충돌의 화면 예시가 맞으면 완료된다. 플레이어가 Sophie의 제안을 받아들였다면 이번에는 Sophie가 문제를 예방한 기록이 남는다. 관계가 나쁘더라도 PR과 공용 문서로 합의할 수 있다.

## C02 M06 버튼 바깥의 중복

### 발단

Mina가 두 작업자를 같은 시점에 시작한 테스트를 보낸다. 순차 요청에서는 통과하던 코드가 주문 두 개를 만든다. 이 가능성은 이전 업무에서 예고돼 있으므로 숨겨진 반전처럼 연출하지 않는다.

**Mina:** “확인하고 저장하는 사이에 둘 다 들어갔어요.”

**플레이어:** “키가 있는지 먼저 보는 것만으로는 안 되네요.”

**Daniel:** “맞아요. 누가 먼저 맡았는지를 한 번에 정해야 해요. 저장소 쪽 약속을 보세요.”

### 플레이

테스트용 저장소가 제공하는 원자적 `claim(key, payload)`와 `complete(key, order)` 계약을 사용한다. 이미 생성 중인 요청은 새 주문을 만들지 않고 같은 완료 결과를 기다린다. 생성 실패 시 선점이 정리돼 올바른 재시도가 가능하다.

멱등성의 개념은 AI 힌트에서 택배 접수증 비유와 작은 타임라인으로 먼저 설명한다. 구현 방식의 정답을 한 가지로 제한하지 않고, 동일한 병렬 결과와 복구 계약을 만족하면 통과한다.

### 검증 예시

| 입력 또는 상황 | 기대 결과 |
|---|---|
| 같은 상점과 키의 순차 요청 두 번 | 주문 하나와 같은 ID |
| 같은 상점과 키의 동시 요청 두 번 | 주문 하나와 같은 ID |
| 같은 키와 다른 내용 | 명시적인 충돌 |
| 다른 상점의 같은 키 | 별개의 주문 두 개 |
| 첫 생성 작업의 실패 후 재시도 | 실패가 고정되지 않고 한 번 생성 |
| 빈 키 | 주문 생성 없이 요청 오류 |
| 완료 응답을 잃은 뒤 재시도 | 새 주문 없이 기존 결과 반환 |
| 로그를 기록하는 정상·실패 경로 | 허용된 추적 정보만 남음 |

### 완료와 복구

필수 계약 테스트를 통과하고, PR에 어떤 경우를 해결했는지 남기면 완료된다. 장시간 막히면 Daniel과 페어링하며 두 수정안을 비교한다. 도움받는 경로도 자신의 말로 결과를 설명하는 짧은 확인을 거친다. CI 실패 횟수는 이 학습 과정에서 관계를 깎는 기준으로 사용하지 않는다.

## C02 M07 고쳤다는 말의 조건

### 발단

Alex가 고객에게 “고쳤다”고 말해도 되는지 묻는다. 패치 병합과 고객의 실제 해결은 다른 시점이다. 플레이어는 달빛상점만 제한 적용하고 관찰 기준을 정한다.

**Alex:** “지금 연락하면 오늘 저녁부터 안심하셔도 된다고 말해도 돼요?”

**선택 A:** “적용됐고 확인 중이라고 먼저 안내하죠. 종료는 오늘 관찰 뒤에요.”

**선택 B:** “정상 주문과 재시도 표본을 확인한 뒤 완료라고 보내겠습니다.”

**선택 C:** “우선 고객이 한 번 써 보고 알려 주면 어떨까요?”

**Yuri:** “사용해 보시라고 할 수는 있어요. 다만 우리 쪽 확인도 같이 해야 해요. 고객이 테스트 담당자는 아니니까요.”

### 플레이

Monitor에 전후 비교 카드가 나타난다. 하나는 중복 0건이지만 전체 주문도 0건이고, 다른 하나는 정상 주문과 재시도가 모두 관찰돼 있다. 플레이어는 어느 자료가 해결 근거인지 판단한다. 고정된 대기 시간을 견디는 대신 가속된 관찰 구간을 직접 진행한다.

오류율, 요청 수, 재시도 결과, 고객 문의를 같이 확인한다. 실제 서비스가 아니라 시나리오 데이터로 변화한다. 관찰 결과는 플레이어의 계약 테스트와 선택한 적용 범위를 반영한다.

### 완료와 복구

현재 확인 범위와 다음 확인 시점, 담당자가 기록되면 완료된다. 기준에 못 미치면 관찰을 더 하거나 제한을 유지하거나 되돌릴 수 있다. 올바른 되돌리기는 미션 실패가 아니다. 복구 경로에서 같은 검증 도구를 사용해 제한 적용을 다시 진행한다.

예방과 검증이 좋았다면 잡아야 할 새 장애를 추가하지 않는다. Sophie가 “오늘 주문 버튼 누른 사람들이 이거 고친 건 모르겠죠?”라고 말하고 Mina가 “그게 잘된 거죠”라고 답한다.

## C02 M08 저녁 여섯 시의 답장

### 발단

Yuri가 고객 답장 초안을 요청한다. 플레이어는 변경 내용, 고객이 할 일, 남은 제약, 추가 문의 경로를 담는다. 코드 내부 용어를 고객에게 외우게 하지 않는다.

“주문을 처리하는 동안 같은 요청이 다시 전달되면 새 주문이 만들어지던 부분을 수정했습니다. 이제 같은 구매 시도는 기존 주문으로 연결됩니다. 현재 달빛상점에 적용했고 정상 주문과 재시도 결과를 확인했습니다. 이미 중복으로 생성된 주문은 별도로 확인하고 있으며, 담당자가 처리 결과를 안내드리겠습니다.”

**플레이어 선택 B:** “같이 정한 규칙이 없었으면 다시 고쳤을 것 같아요.”

## 제작에 필요한 콘텐츠

준비할 파일은 주문 요청 모듈, 테스트용 저장소 인터페이스, 요청과 화면 응답 예시, 공개 계약 테스트, 별도 CI 계약 테스트, 가상의 로그 표본, 지원 티켓, API 정책 문서다. 실제 저장소 경로와 파일 분할은 구현 시 기존 `content/commerce-api/{ko,en}` 체계에 맞춘다.

숨겨진 CI는 공개된 정책에서 조합을 넓힌다. 위키에 없는 만료 규칙이나 실제 DB 지식을 갑자기 요구하지 않는다. 일부 구현 문자열을 포함했는지보다 동작과 불변 조건으로 판정한다. PR 설명과 고객 답장도 키워드 하나를 맞히기보다 필요한 정보 칸이 채워졌는지 확인한다.

AI 위임 초안은 의도적으로 **순차 재시도만 처리하는 구현**으로 제안한다. 초안 설명에 “동시 요청까지 검증하지 않았다”고 표시해 플레이어가 범위를 확인할 수 있게 한다. 실패를 숨겨 놀라게 하는 장치보다 제한이 있는 유용한 도구로 다룬다.

## 완료 기준과 검증 경로

챕터 완료에는 재현 근거, 중복 방지 계약, 로그 기준, 화면 합의, 배포 확인, 고객 설명이 필요하다. 반드시 직접 모든 코드를 타이핑해야 할 필요는 없다. 동료와 AI 초안을 이용해도 결과를 확인할 수 있으면 된다.

검증 경로는 직접 구현, 힌트와 페어링, 화면 완화 선행, 서버 수정 선행, 초기 로그 과다 후 수정, 제한 배포 후 되돌리기, 동시성을 먼저 해결한 숙련 플레이의 일곱 가지를 우선 확인한다. 중간 저장 후 재개 시 이미 보낸 고객 답장을 중복 발송하지 않고 관찰 단계와 합의 상태를 유지해야 한다.

핵심 대사는 현재 시나리오의 한국어 초안이다. 영어판은 직역하기보다 고객의 업무 의미와 인물의 말투를 보존하도록 별도 검토한다. 화면 폭, 이름 길이, 로그와 코드의 줄바꿈도 한국어와 영어 모두에서 확인한다.
