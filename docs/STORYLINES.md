# 멀티 스토리라인과 이벤트 시나리오 설계

기획 버전 0.2 · 2026년 11월 24일 · 논의용 초안

지금까지의 본편은 **한 줄의 주 스토리**(ATLAS와 커리어, 12챕터 96업무)에 선택 사건이 붙는 구조였다. 이 문서는 이를 세 층으로 재구성한다.

| 층 | 역할 | 플레이어가 느끼는 것 | 분량 단위 |
|---|---|---|---|
| **주 스토리(Spine)** | 회사·제품·ATLAS의 큰 흐름. 모든 플레이어가 지나감 | "이 회사에서 무슨 일이 벌어지고 있나" | 챕터, 주 업무 |
| **스토리라인(Arc)** | 플레이어가 고르고 키우는 병렬 이야기 6~8개 | "나는 어떤 개발자가 되고 있나" | 아크 단계(비트) 4~7개 |
| **이벤트(Event)** | 조건이 맞으면 끼어드는 짧은 장면. 덱에서 뽑힘 | "회사생활은 계획대로 안 된다" | 카드 1장 = 1~5분 |

기존 [장편 시나리오](SCENARIO.md), [인물과 분기](SCENARIO_CHARACTERS.md), [96개 업무](SCENARIO_MISSIONS.md)는 주 스토리의 기준으로 유지한다. 이 문서의 아크와 이벤트는 그 위에 얹는 층이며, 현재 구현된 것은 없다.

---

## 1. 핵심 원칙

1. **시간은 한정, 아크는 많다.** 한 시점에 깊게 진행할 수 있는 아크는 최대 2개(“관심 슬롯”). 무엇을 키우는지가 곧 선택이다. 모든 아크를 한 번에 완주할 수 없어서 2회차의 이유가 생긴다.
2. **아크는 주 스토리를 대체하지 않고 색을 바꾼다.** 같은 장애(예: 성수기 출시)를 오픈소스 아크 플레이어는 라이브러리 메인테이너로, 사이드 프로젝트 아크 플레이어는 퇴근 후 피곤한 사람으로 겪는다.
3. **이벤트는 처벌이 아니라 결이다.** 나쁜 이벤트도 회복 경로가 있다. 랜덤 이벤트 하나로 엔딩이 막히지 않는다.
4. **모든 분기는 실제 플레이로 증명한다.** 대사 선택만으로 아크가 끝나지 않는다. 코드·PR·리뷰·문서·관찰 같은 산출물이 비트의 완료 조건이다.
5. **책상이 변한다.** 아크와 직급은 내 책상(모니터, 소품, 메모, 조명)에 흔적을 남긴다. 플레이어는 화면 밖을 보면서 자신의 경로를 확인한다.

## 2. 스토리라인(아크) 목록

각 아크는 **입구 → 비트 → 갈림길 → 결말**로 구성한다. 입구는 대개 이벤트 카드로 열린다.

### A. 이직선 — “다른 책상” (Jamie, Brightloop)
- **입구:** Connectly 오퍼(챕터 1 이미 구현), 이후 커피챗 이벤트.
- **비트:** 커피챗 → 과제 전형(실제 코드 과제, 회사 업무와 시간 경쟁) → 레퍼런스 체크(동료 관계가 반영) → 오퍼 협상(연봉 vs 역할 vs 리모트) → 퇴사 통보와 인수인계 → Brightloop 온보딩.
- **갈림길:** 협상에서 무엇을 우선하나 / 퇴사 통보를 누구에게 먼저 하나 / 카운터오퍼 수락 여부.
- **결말:** Brightloop 경로(주 스토리 3구간 분기), 카운터오퍼로 잔류(관계 일부 변화), 과제 포기.
- **충돌:** 사이드 프로젝트 아크와 시간 경쟁. 인수인계 품질이 `handoff_quality`에 반영.

### B. 사이드 프로젝트선 — “내 크기의 제품”
- **입구:** 달빛상점 장부 사진 이벤트(구현됨) 또는 Lounge 게시판의 “소상공인 도구” 글.
- **비트:** 주말 프로토타입(브라우저 앱에 새 탭 ‘My Project’) → 첫 사용자 3명 → 회사 코드와의 경계 문제(겸업 규정) → 유료화 결정 → 런칭 주말과 본업 장애가 겹침.
- **갈림길:** 회사 자산을 참고할까 / 겸업 신고 / 본업 장애 날 어디로 가나.
- **결말:** 작은 제품 엔딩(진로 장면 4), 회사가 인수해 사내 기능으로, 조용히 오픈소스로 공개, 접고 본업 집중.
- **책상 흔적:** 개인 노트북이 책상 왼쪽에 추가, 사용자 피드백 포스트잇.

### C. 오픈소스선 — “남의 저장소에 첫 PR”
- **입구:** 업무 중 쓰는 라이브러리 버그 발견 이벤트(주문 날짜 파싱).
- **비트:** 이슈 작성 → 첫 외부 PR(낯선 메인테이너의 리뷰 문화) → 회사에서 패치 버전 사용 여부 논쟁 → 메인테이너 제안 → 컨퍼런스 발표 제안.
- **갈림길:** 회사 시간에 기여해도 되나(Alex 설득 vs 개인 시간) / 메인테이너 수락 / 발표에서 회사 사례를 얼마나 공개하나.
- **결말:** 메인테이너(깊이 파는 사람), 발표 후 채용 제안 증가(A와 연결), 번아웃 후 인계.

### D. 리드선 — “같이 끝내는 사람” (Alex, Daniel)
- **입구:** 챕터 4 Daniel의 리뷰 병목 이벤트에서 “리뷰 분담 제안”.
- **비트:** 리뷰 로테이션 운영 → 신입 지우 온보딩(멘토링) → 첫 1:1 → 일정 협상에서 Alex와 대립 → 파트 리드 제안.
- **갈림길:** 지우의 PR을 대신 고칠까 설명할까 / 일정 약속을 막을까 흡수할까 / 리드 제안 수락.
- **결말:** 팀 리드(진로 장면 2), 기술 리드에 남기, 관리 거절 후 시니어 IC.
- **책상 흔적:** 1:1 노트, 화이트보드 일정표, 모니터 옆 팀 사진.

### E. 조사선 — “오래된 번호의 원래 주인” (LEGACY-17, Taeseok)
- **입구:** 챕터 2 말 LEGACY-17 예고(구현됨).
- **비트:** 감사 로그 대조(Request Lab 확장: 로그 질의) → 예전 결제 서비스 담당자 찾기(퇴사자 연락) → 당시 결정의 이유 문서 발견 → 보안팀과 범위 협의 → 이관 계획.
- **갈림길:** 퇴사자에게 연락할까 / 발견한 불일치를 언제 보고하나 / 삭제 vs 유지 계획.
- **결말:** 기술 전문가(깊이 파는 사람), 보안팀 이동 제안, 조사 공유 후 다른 사람에게 넘김.

### F. 동료선 — 인물별 짧은 아크 (Sophie / Mina / Daniel)
- **Sophie:** 질문하던 후배 → 자신의 설계를 지키는 동료 → 플레이어와 설계 회의에서 반대(“친구의 설계를 반대하는 회의”).
- **Mina:** 자동화 주인이 되기 → 번아웃 신호 이벤트 → 휴직/팀 이동/역할 재정의.
- **Daniel:** 병목 → 관리 vs 전문 기술 고민 → 퇴사 또는 아키텍트 이동(“떠나는 사람에게 묻는 질문”).
- 관계 수치가 아니라 **함께한 사건의 기록**으로 진행. 한 명에게 집중하면 다른 동료 아크는 배경으로 흘러간다(놓친 장면은 후일담 메시지로 회수).

### G. 생활선 — “잠시 자리를 비운다”
- **입구:** 컨디션 저하가 누적되거나 야근 3회 이상.
- **비트:** 수면 부족 이벤트 → 병원/상담 선택 → 휴식 협상(팀장과) → 이사·통근 결정 → 복귀.
- **갈림길:** 휴가를 쓸까 / 이사로 통근을 줄일까(비용) / 퇴근 후 공부 vs 휴식.
- **결말:** 지속 가능한 리듬(오래 일하는 사람), 휴직 후 복귀(잠시 자리를 비운다), 이 아크를 무시하면 다른 아크 비트가 지연.
- **책상 흔적:** 책상 위 약병→물병, 창밖 풍경(이사하면 집 근처 사무실 창 변경은 제외, 대신 책상 사진).

### H. AI 파트너선 — “AICode가 동료가 될 때”
- **입구:** AI 위임 3회 이상.
- **비트:** AI 초안의 한계 기록 → 사내 자동화 파일럿 담당 → 성과 보고서 작성(`automation_report`) → 자동화로 역할이 줄어든 동료와 대화 → 정책 제정.
- **갈림길:** 성과를 부풀릴까 정확히 측정할까 / 리뷰 단계를 줄일까.
- **결말:** 자동화 리드, 다시 배울 자리(진로 장면 7), 신중한 도구 관리자.

### I. 평판선 — “익명 게시판의 나” (Lounge, DevDaily)
- **입구:** 브라우저 Lounge에 회사 이야기가 올라옴.
- **비트:** 익명 글에 답할까 → 기술 블로그 연재 → 사내 정보 노출 실수 위험 → 업계 인지도 → 채용 제안 폭증(A, C와 연결).
- **갈림길:** 회사 비판 글에 반박/공감/무시 / 블로그에 장애 회고를 얼마나 공개하나.
- **결말:** 업계에 알려진 개발자, 조용한 장인, 정보 노출 징계 후 회복.

### 아크 간 관계
```
A 이직 ──경쟁── B 사이드         C 오픈소스 ──강화── A 이직
D 리드 ──경쟁── E 조사(시간)      I 평판 ──강화── A·C
G 생활 ──조건── 모든 아크(무시하면 비트 지연)
F 동료 ──교차── D·E·H(같은 사건을 다른 사람의 시점으로)
```

### 관심 슬롯
- 활성 아크 최대 2개. 새 아크의 입구 이벤트에서 “지금은 못 해요”를 고르면 아크는 **보류**로 남고, 나중에 다시 열 수 있다(입구 이벤트 재등장).
- 아크를 내려놓는 것도 선택지. 내려놓은 아크는 다른 인물이 이어받아 진행되고, 후일담으로 결과가 온다.

## 3. 이벤트 시나리오 시스템

### 이벤트 카드 형식
```text
id          고유 ID (예: ev_outage_3am)
category    daily | office | crisis | life | industry | arc
format      chat | call | desk_visit | popup | scene | minigame
trigger     day/chapter 범위, 시각 창, 직급, 관계·컨디션·돈 임계, 플래그, 활성 아크
weight      기본 가중치 (+조건별 보정)
cooldown    같은 카테고리 재등장 간격(일)
once        1회성 여부
choices     선택지 (각자 결과·비용·후속 카드)
chain       다음 카드 예약 (n일 뒤, 시각, 조건)
desk        책상 연출 (전화 진동, 누군가 책상 옆에 섬, 포스트잇 추가 등)
```

- **덱 방식:** 하루 시작 시 조건을 만족하는 카드 중 가중치 추첨으로 0~2장을 오늘의 이벤트로 예약. 미션 진행 중 시간에 맞춰 발동한다. 1회성 스토리 카드(아크 입구)는 우선순위가 높다.
- **피로도 제어:** 하루 위기(crisis) 카드 최대 1장. 연속 이틀 위기 금지. 컨디션 낮으면 생활 카드 가중치 상승.
- **형식별 연출**
  - `chat`: 지금처럼 메신저 선택지.
  - `call`: 책상 위 휴대폰 진동 → 화면 하단 통화 UI. 무시 가능(부재중 기록).
  - `desk_visit`: 모니터 옆에 동료가 다가와 섬(실루엣 + 말풍선). 화면을 잠깐 가린다. 데스크 뷰의 핵심 연출.
  - `popup`: OS 알림(보안 교육, 설문, 사내 공지).
  - `scene`: 모니터가 꺼지고 짧은 컷(회식, 컨퍼런스, 면접). 텍스트 + 일러스트 카드.
  - `minigame`: 짧은 상호작용(장애 대응 3분 타이머, 리뷰 빨리 읽기, 화이트보드 그리기).

## 4. 책상(워크스테이션) 진화

게임 화면의 기본은 **내 책상**이다. 모니터가 중앙에 크게, 책상과 창, 소품이 둘레에 보인다. F2로 화면 가까이 보기.

## 5. 데이터 구조 초안

```gdscript
Game.state["arcs"] = {
    "offer":  {"stage": 2, "status": "active", "beats": {"coffee_chat": "done"}, "since_day": 9},
    "side":   {"stage": 0, "status": "deferred"},
    ...
}
Game.state["events"] = {"fired": {"ev_outage_3am": 12}, "queue": [{"id": "ev_retro_req", "day": 13, "minutes": 570}]}
```
- 아크 정의: `scripts/story/arcs/<id>.gd` (미션과 같은 형식의 비트 목록 + 진입/충돌 규칙)
- 이벤트 정의: `content/events/<category>.json` (카드 데이터) + 필요한 경우 스크립트 훅
- 기존 `SideEvents`의 SCHEDULE은 “고정 카드”로 흡수한다.

## 6. 제작 순서 제안

1. **이벤트 엔진**: 카드 데이터, 덱 추첨, 체인, 형식 `chat`/`call`/`desk_visit`/`popup`. 기존 곁가지 사건 이관. 카드 10장.
2. **아크 엔진 + 2개 아크 시범**: A 이직(이미 소재 있음)과 E 조사(LEGACY-17로 챕터 3 연결). 관심 슬롯.
3. **챕터 3 제작**: 주 스토리 + 두 아크 비트가 실제로 교차하는지 확인.
4. 나머지 아크와 카드 확장, 2회차 요소.

**결정이 필요한 것**
- 활성 아크 슬롯 수(2개 제안).
- 랜덤성의 정도: 완전 랜덤 덱 vs 챕터별로 큐레이션된 덱(제안: 큐레이션 70% + 랜덤 30%).
- 첫 시범 아크 2개 선택.
