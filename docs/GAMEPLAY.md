# Developer Life Simulator 게임성 설계

플레이의 중심은 **정보를 모아 원인을 추리하고, 작게 실험하고, 결과를 확인하는 재미**다. 커리어가 진행되면 기술 문제를 푸는 것에 더해 시간과 범위, 동료의 역할을 선택한다. 긴 스토리의 각 업무가 서로 다른 판단을 요구하도록 만든다.

플레이어는 자신의 책상에 앉은 시점으로 출근한다. IDE, 터미널, 메신저는 눈앞의 모니터에서 직접 조작한다. 작은 글씨를 읽을 때는 모니터에 가까이 다가갈 수 있고, 한발 물러나면 키보드, 머그, 창밖 풍경을 다시 볼 수 있다. 같은 자리에서 하루를 시작하고 마친다.

개발 업무는 실제 소스 코드, 테스트, Git, 리뷰와 배포로 진행한다. Packet Run과 달빛상점은 개발 업무에서 다루는 제품이다. 플레이어는 Relay에서 Packet Run을 플레이하거나 상점의 주문을 눌러 배포한 결과를 확인할 수 있다.

플레이 중 느끼는 자율성과 유능감이 게임의 재미, 선호도와 연관된다는 실험 연구를 참고했다. 이 게임에서는 역할을 고른 결과가 다른 업무로 이어지는지, 테스트와 주문 기록만 보고 스스로 다음 행동을 정할 수 있는지로 구체화했다. [Ryan, Rigby & Przybylski, 2006](https://selfdeterminationtheory.org/wp-content/uploads/2020/10/2006_RyanRigbyPrzybylski_MandE.pdf)

외부 플레이테스트에서는 코딩 경험 유무별로 첫 PR까지 걸린 시간, 막힌 앱과 행동, 스스로 이해했다고 설명할 수 있는 업무 결과를 기록한다. 챕터 5~6에서는 이직했을 때 실제로 달라진 일을 기억하는지, 리허설에서 실패한 이유를 표본만 보고 찾는지를 확인한다. 다음 볼륨은 파일럿 일정이 후배와 함께 처리할 실제 고객 요청을 바꾸는 챕터 7, 그리고 달빛상점이나 Packet Run의 출시 뒤 사용자 제보가 다음 수정으로 이어지는 선택 업무에 우선 배정한다.

## 이번에 구현한 변화

TaskBoard에 업무 보드와 조사 노트를 나눴다. 이름 버그, 닉네임 회귀, 쿠폰 리뷰, 배송비 충돌, 로그인 장애, 쿠폰 핫픽스의 여섯 업무에 각각 단서와 세 가지 원인 가설이 있다. 단서는 실제 정책 열람, 파일 읽기, 실패 테스트, 관련 Git 기록, PR diff, 장애 로그와 충돌 결과에서 쌓인다.

단서를 하나 확인하면 가설을 기록할 수 있다. 완료 전까지 바꿀 수 있고 틀렸다고 신뢰나 돈을 잃지 않는다. 원인 후보는 표면상 비슷해 보이는 설명으로 구성한다. 명백히 엉뚱한 답 두 개 사이에서 정답을 고르는 퀴즈를 목표로 하지 않는다.

가설 선택은 실제 코드, 리뷰와 CI를 대신하지 않는다. 가설을 맞혔어도 리뷰를 제출하지 않으면 쿠폰 결함은 그대로 출시될 수 있다. 업무가 끝나면 기록한 가설, 실제 결과와 배운 점이 Dashboard의 조사 수첩에 남는다. 후속 핫픽스로 회복한 경우 원래 리뷰 기록에도 그 사실이 이어진다.

일괄 적용되던 CI 실패의 기술 신뢰 감점과 AI 초안의 CI 실패 감점을 제거했다. 실패한 테스트를 가진 브랜치를 올렸을 때도 확인 방법을 안내한다. 회고와 통계 화면은 실패 횟수를 잘못의 점수처럼 강조하지 않는다. 운영 장애와 승인 우회 같은 행동의 결과는 별도로 남는다.

새 조사는 업무 시작 시 알려 주며, 단서 카드는 해당 도구나 문서로 이동할 수 있다. Terminal 단축 버튼은 창만 열고 명령을 자동 실행하지 않는다. 기록은 저장 후 재개해도 유지되며, 조사 데이터가 없는 이전 저장 파일에서도 새 업무부터 사용할 수 있다.

챕터 2 첫 세 업무에는 Request Lab을 추가했다. 고객 티켓과 같은 요청의 기록을 비교하고, 응답 지연·재전송·요청 키·클릭 수를 바꿔 실제 TypeScript 주문 함수를 실행한다. 조건에 따라 호출 수와 생성된 주문 수·식별자가 달라진다. 응답 지연 자체는 가상 조건이며 실제 네트워크나 결제를 사용하지 않는다.

수정한 파일을 덮어쓰지 않고 신고된 버전을 다시 실행할 수 있다. 실험 기록은 저장되며 현재 코드의 검증 뒤 파일을 바꾸면 해당 검증을 다시 해야 한다. 순차 중복 방지 업무는 실험만으로 완료되지 않는다. 실제 로컬 테스트와 PR·CI·동료 검토도 필요하다. 구간 종료는 순차 계약 검증으로 표현하고 동시 요청·운영 배포를 완료했다고 표시하지 않는다.

이 아래는 장편 본편에 적용할 후속 설계다. 업무 전략, 성장 도구, 난이도 프로필을 이미 구현한 기능으로 취급하지 않는다.

## 한 업무의 플레이 흐름

| 단계 | 플레이어가 하는 판단 | 게임이 보여주는 피드백 |
|---|---|---|
| 요청 파악 | 무엇이 확인됐고 무엇이 모르는 사실인가 | 고객 표본, 영향 범위, 질문 |
| 조사 | 어떤 정보를 먼저 확인할 것인가 | 서로 연결되는 단서와 실패 사례 |
| 가설 | 어느 원인이 현상을 설명하는가 | 가설 기록과 검증할 예시 |
| 실험 | 어떤 작은 변경으로 가정을 확인할 것인가 | 실제 테스트, diff, 시뮬레이션 결과 |
| 범위 선택 | 지금 어디까지 적용할 것인가 | 시간, 지원, 고객 영향의 차이 |
| 종료 확인 | 무엇을 근거로 끝났다고 말할 수 있는가 | 고객 결과, 동료 인계, 남은 제약 |
| 보상 | 무엇을 배웠고 다음 일에 무엇이 남는가 | 조사 수첩, 도구 개선, 생활과 관계의 변화 |

모든 단계가 매번 별도의 버튼이 되지는 않는다. 이미 조사한 근거는 자동으로 기록하고, 숙련자는 코드부터 고친 뒤 검증해도 된다. 조사 노트를 채워야 병합할 수 있는 식의 추가 관문을 만들지 않는다.

## 업무 유형의 차이

| 유형 | 재미의 중심 | 대표적인 선택 | 피해야 할 반복 |
|---|---|---|---|
| 버그 조사 | 현상을 설명하는 원인 찾기 | 재현 조건과 실험 순서 | 매번 같은 파일에서 TODO 찾기 |
| 기능 개발 | 여러 요구를 작은 계약으로 만들기 | 범위와 경계값 | 구현 방법을 한 문자열로 강요 |
| 코드 리뷰 | 코드와 규칙의 차이를 찾기 | 근거와 수정 제안 | 틀린 줄을 무작정 많이 선택 |
| 병합과 이관 | 서로 맞던 변화가 합쳐질 때의 문제 | 보존할 의미와 호환 범위 | 충돌 기호만 지우기 |
| 장애 대응 | 영향 제한과 정보 정리를 함께 하기 | 복구, 축소, 관찰, 공지 | 시간제한에 쫓겨 명령 암기 |
| 멘토링 | 다음 사람이 스스로 할 수 있게 돕기 | 직접 수정, 설명, 페어링 | 친절한 말투만 정답으로 판정 |
| 운영과 종료 | 한 일이 실제로 끝나는 조건 정하기 | 확인 범위와 인계 | 초록색 배지만 보고 완료 |

한 챕터의 여덟 업무 중 고강도 조사·구현은 두세 개를 중심으로 묶고, 나머지는 짧은 실험, 협의, 리뷰와 결과 확인으로 리듬을 만든다. 같은 Git 절차는 큰 사건 사이의 흐름으로 묶는다.

## 시간과 업무 전략

게임 시간은 의미 있는 행동과 합의한 작업으로 진행한다. 문서를 읽거나 코드를 생각하는 현실 시간에 자동으로 계속 줄어들지 않는다. 앱을 빨리 바꾸는 반사 신경과 읽기 속도가 커리어의 주 평가가 되지 않게 한다.

후속 개발에서는 긴 업무의 시작에 범위, 검증, 지원의 조합을 고르게 한다. 세 버튼 모두 정당한 이유와 구체적인 대가가 있어야 한다.

| 예시 전략 | 얻는 것 | 지불하거나 확인할 것 |
|---|---|---|
| 작게 먼저 적용 | 빨리 고객 영향을 줄임 | 남은 대상과 확대 일정 |
| 충분히 재현한 뒤 적용 | 더 넓은 검증 근거 | 초기 관찰과 재현에 쓰는 시간 |
| 동료와 병렬 진행 | 빠른 원인 분리와 공유 맥락 | 상대의 가용 시간과 합의된 분담 |

전략은 마법 같은 테스트 통과율이나 숨은 주사위 보너스를 주지 않는다. 먼저 얻는 정보, 적용할 수 있는 고객 범위, 동료가 처리하는 작업을 바꾼다. 시나리오가 임의로 시각을 건너뛰더라도 이미 확보한 시간 이점과 지원 약속을 무효화하지 않도록 일정 처리를 함께 고친다.

의도치 않은 지연에는 상황 공유와 범위 재합의가 열린다. 납기를 한 번 놓쳤다고 임무가 영구적으로 막히지 않는다. 미래의 문제를 피하기 위해 무조건 출시를 미루는 방법도 정답이 되지 않게 고객의 비용과 다음 지원 일정이 실제로 남는다.

## 성장은 더 편하고 넓게 일하는 능력

숙련은 커밋 수나 명령 입력 횟수로 올리지 않는다. 완료한 서로 다른 업무의 증거가 사용 가능한 도구를 늘린다. 같은 행동을 반복해 점수를 파밍하는 방식은 사용하지 않는다.

- 재현을 설명한 경험은 입력 비교 도구와 재현 템플릿으로 이어진다.
- 검증을 남긴 경험은 계약 테스트 묶음과 자동 대조 도구로 이어진다.
- 인계가 실제로 수행된 경험은 동료에게 맡길 수 있는 작업 범위로 이어진다.
- 고객에게 적용 결과를 설명한 경험은 다음 문의의 배경과 지원 자료를 풍부하게 한다.

이 도구들은 실제 행동을 줄여야 한다. 초반에 직접 비교한 여러 줄의 주문 기록이 후반에는 대조 보고서 한 장으로 정리되고, 플레이어는 차이가 있는 부분에 집중한다. 성장한 뒤에도 같은 단순 작업을 더 큰 숫자로 반복시키지 않는다.

직급이 높아져도 테스트 판정을 유리하게 바꾸지 않는다. 더 어려운 문제를 설명하고, 더 많은 일을 나누고, 더 좋은 도구를 선택할 수 있게 한다. 기술 경로와 리드 경로는 같은 상위 단계에 도달하는 다른 플레이 방식이다.

### 구현: 커리어 층 (`scripts/story/career.gd`)

- **스킬 5종** 디버깅·테스트·협업·운영·제품. 경험치는 서로 다른 업무의 증거에서 온다: 리뷰 코멘트, 조사 단서, 문서 제출, 내 PR의 CI 첫 통과(PR당 1회), 병합, 제품 출시, 온콜 대응. 반복 행동은 하루 한도가 있다(테스트 3회, 답장 5회, Monitor 2회). 커밋 자체는 경험치를 주지 않는다.
- **특성** 은 편안함만 바꾼다. 테스트 판정은 바꾸지 않는다: 협업 2 신뢰 상승 +1, 운영 2 컨디션 소모 −20%, 제품 3 일급 +10%, 테스트 3 테스트 시간 단축, 디버깅 3 AI 토큰 +25%.
- **오늘의 목표 3개** 는 그날 업무에 맞게 뽑힌다. 횟수가 아니라 좋은 습관을 본다: 고치기 전에 실패를 먼저 재현하기, CI가 잡은 문제를 고쳐 다시 통과시키기, 다음 사람을 위한 테스트 남기기, PR 설명에 확인한 범위 적기, 리뷰 코멘트, 동료에게 답하기, 딴짓 들키지 않기, 컨디션 지키기. 진행 상황은 TaskBoard 상단, 보조 모니터, Dashboard에 보이고 달성마다 8,000원과 경험치를 준다.
- **하루 평가** S(목표 3개 + 적발 0)·A·B·C. CI 실패는 평가를 깎지 않는다. CI가 문제를 잡는 건 제대로 일한 것이다. 퇴근 화면 왼쪽에 평가, 목표, 오늘 얻은 경험치를 보여 준다.
- **업적 20개** 는 Dashboard 트로피 선반에 모인다. 잠긴 업적은 이름을 숨긴다.

## 보상과 수집

즉시 보상은 성공한 테스트와 수정 전후의 차이, 업무 보상은 고객의 실제 변화, 장기 보상은 성장한 도구와 관계다. 조사 수첩은 초반의 수집 요소이며, 모든 칸을 채우는 것을 엔딩 조건으로 두지 않는다.

책상 물건에는 고객과 동료의 기억을 연결한다. Sophie가 준 메모, 첫 행사 뒤의 간식 상자, 만든 도구의 작은 스티커처럼 플레이의 흔적이 쌓인다. 장비 구매는 편안함과 꾸미기를 제공하고, 기본 도구가 불편해야 구매 가치가 생기는 구조는 피한다.

예방에 성공하면 큰 사건을 강제로 발생시키는 대신 자동으로 통과하는 확인 단계, 평온한 고객 답장, 함께 쉬는 장면을 준다. 플레이어가 준비한 것이 실제 일을 줄였다는 것이 가장 큰 보상이다.

## 관계 선택의 재미

관계 선택은 동의 버튼을 반복하는 게임이 되지 않는다. 요구를 수용할지, 범위를 조정할지, 근거를 더 모을지, 다른 담당자에게 요청할지를 선택한다. 친밀한 동료도 반대하고, 사적으로 어색한 동료도 확인된 약속은 지킨다.

일정과 품질 중 하나만 선택하는 가짜 딜레마보다 세 번째 계획을 만들 수 있게 한다. 기능 한 개를 빼거나, 고객 일부만 열거나, 지원 가능한 시간대로 옮기는 선택이다. 비용이 없는 완벽한 답을 매번 추가하지는 않는다.

결과는 관계 숫자와 함께 실제 다음 행동으로 보여준다. 좋은 인계 뒤에는 휴일 연락이 줄고, 불분명한 설명 뒤에는 같은 질문이 다시 온다. 플레이어가 방식을 바꾸면 후속 행동도 바뀐다.

## 난이도와 도움

후속 난이도 프로필은 같은 이야기를 유지하면서 안내와 동시 과제 수를 조정한다.

| 프로필 | 안내 | 도전 |
|---|---|---|
| 편하게 경험 | 관련 파일과 재현 예시, 동료 페어링을 먼저 제시 | 한 번에 한 문제에 집중 |
| 기본 | 증상과 정책부터 제공, 단계별 힌트 선택 | 원인과 검증 순서를 스스로 구성 |
| 숙련 | 간결한 지원 티켓과 넓은 사용 사례 | 복합 예외와 여러 작업의 우선순위 |

도움 사용 횟수를 성과 면담의 감점이나 엔딩 봉쇄로 쓰지 않는다. 난이도 변경은 진행 중 허용한다. 어려운 모드는 고정 대기를 늘리거나 오타를 더 엄격하게 잡는 방식으로 만들지 않는다.

## 다음 제작 우선순위

첫째는 챕터 2의 중복 주문 업무에 조사와 작은 실험을 연결하는 것이다. 현재 조사 노트의 자료를 표시하는 기능에서 한 단계 나아가, 재현 조건을 바꿔 결과 차이를 관찰하게 한다. 동료의 설명과 코드 실행이 서로 맞물려야 한다.

둘째는 업무 전략과 실제 범위·지원의 차이다. 최소 하나의 업무에서 세 접근이 서로 다른 첫 정보를 주고 모두 완료될 수 있게 만든 뒤 확장한다.

셋째는 반복 작업을 줄이는 성장 도구와 장편의 역할 분담이다. 조사 수첩 수치만 늘리는 대신 이전에 만든 결과가 다음 챕터의 작업량을 실제로 줄이도록 한다.

넷째는 컨디션과 휴식, 딴짓 이벤트의 조정이다. 합의한 휴식과 업무 조사 중 다른 창을 읽는 일을 무조건 적발 위험으로 처리하지 않는다. 단속 미니게임의 긴장도는 선택적으로 완화할 수 있게 한다.

## 검증

이번 구현은 별도 프로젝트와 저장 영역을 만드는 `tools/run_gameplay_tests.ps1`로 검증한다. 플레이어의 저장과 Git 저장소는 테스트에 사용하지 않는다. 자동 확인에는 관련 없는 단서 배제, 실제 실패와 실행 실패 구분, 잘못된 가설 수정, 중복 이벤트, 다른 PR과의 분리, 후속 회복, 저장·재개, 이전 저장 파일, 한글·영문 UI와 출처 이동을 포함한다.

렌더 검증은 같은 테스트 실행에 `-Screenshots`를 붙여 두 언어의 이미지를 `build/gameplay-qa`에 저장한다. 테스트가 통과했다는 사실만으로 재미가 입증되지는 않는다. 첫 사용자에게 설명 없이 플레이를 맡겨 언제 가설을 세우는지, 왜 도구를 여는지, 힌트를 원한 순간과 반복처럼 느낀 순간을 관찰해야 한다.

첫 플레이테스트의 질문은 세 가지다. 원인을 찾았을 때 스스로 알아냈다는 감각이 있었는가, 실패 뒤 다음 실험을 떠올릴 수 있었는가, 해결한 결과가 누군가에게 의미 있게 보였는가. 답이 약하면 콘텐츠 양보다 해당 업무의 단서와 실험부터 고친다.
