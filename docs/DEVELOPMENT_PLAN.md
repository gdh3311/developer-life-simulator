# Developer Life Simulator 개발 실행 계획

기준일 2026년 11월 23일 · 챕터 2 완결

목표는 개발자 회사생활의 조사, 코딩, 협업과 커리어 선택이 재미있는 Windows용 싱글플레이 게임을 완성하고 Steam에 출시하는 것이다. 장편 시나리오의 기준은 12개 챕터, 주 업무 96개, 선택 사건 48개다. 현재는 첫 챕터와 챕터 2 전체 8개 업무가 구현돼 있다.

**가장 먼저 챕터 2의 짧은 구간에서 재미와 제작 방식을 확인한다. 외부 테스트 전에 실행 환경과 배포를 검증하고, 이후 검증된 형식으로 본편을 확장한다.** 콘텐츠를 늘리는 속도보다 완주 가능성, 실제 선택의 차이, 저장 안정성을 우선한다.

## 현재 출발점

| 구분 | 확인한 상태 | 이번 계획에서의 의미 |
|---|---|---|

| 실제 개발 업무 | Git 저장소, Node 테스트, PR·CI·NPC 리뷰 | 핵심 플레이 수단 |
| 최근 게임성 개선 | 여섯 업무의 조사 노트, 가설 수정, 결과 수첩, CI 실패 감점 조정 | 통합 플레이를 확인할 신규 기능 |
| 자동 검사 | 조사 기능 66개 검사 통과, 한국어·영어 렌더 확인 | 기능 검사 결과이며 전체 게임 검증과 구분 |

| 작업 상태 | 최근 코드와 문서 변경이 작업 폴더에 존재 | 변경 검토와 재현 가능한 기준점 필요 |

## 최근 진행 결과

챕터 1의 예방·도움·수습 경로를 실제 Git·Node로 완주하는 자동 검증과, NPC 리뷰·CI 중간 상태의 프로세스 재시작 검증을 추가했다. 조사 기능과 복구 검사까지 총 272개 확인 항목이 통과했다. 수동 UI와 첫 사용자 플레이테스트는 별도로 남는다.

DEV 001의 자동 진행 검증과 DEV 002의 저장 버전·백업·중복 방지 기반을 구현했다. 기존 엔딩을 불러오는 처리와 주요 대기 단계의 재개를 보강했다. 구체적인 결과와 한계는 [챕터 1 검증 기록](QA_CHAPTER_01.md)에 정리한다.

DEV 003의 전환과 DEV 004~006의 첫 플레이 구간을 구현했다. 기존 저장에서 진입해 고객 기록 조사 → 실제 요청 코드의 지연·재전송 실험 → 순차 중복 방지와 PR·CI까지 연결된다. 한국어 직접 수정과 영어 AI 도움 경로를 실제 프로세스 재시작으로 검증했다. 이후 M04~M08(로그 허용 목록, 화면 상태 리뷰, 동시 요청 선점, 제한 적용·관찰, 고객 답장)을 추가해 8개 업무로 챕터를 완결했다. 고객 추가 질문 분기와 동료 페어링은 아직 없다. [챕터 2 구현·검증 기록](QA_CHAPTER_02.md)을 구현 범위의 기준으로 삼는다.

## 개발 원칙

1. 한 작업 묶음은 직접 실행하거나 검토할 수 있는 결과로 끝낸다.
2. 조사 노트는 생각을 돕고, 실제 검증과 리뷰를 대체하지 않는다.
3. 실험 중의 실패와 운영 책임을 구분하고, 도움 사용을 벌주지 않는다.
4. 선택의 차이는 실제 정보, 작업 범위, 동료의 행동과 결과로 보여준다.
5. 새로운 업무 유형을 한 번 완성해 검증한 뒤 여러 챕터에 확장한다.
6. 출시일과 플레이 시간을 확정하기 전에 실제 제작·플레이 시간을 측정한다.
7. 현재 플레이어의 저장과 Git 기록을 개발 테스트의 작업 공간으로 사용하지 않는다.

## 우선순위

| 우선순위 | 다룰 것 | 미루면 생기는 문제 |
|---|---|---|
| P0 | 진행·저장 안정성, 챕터 전환, 중복 주문의 작은 실험 | 다음 챕터를 추가해도 안정적으로 이어서 플레이할 수 없음 |
| P0 외부 배포 조건 | Git·Node 동봉, 실행 격리, Windows export | 개발 환경 밖에서 검증하거나 배포할 수 없음 |
| P1 | 챕터 2 완결, 실제 업무 전략, 컨디션·휴식, 반복 작업 축소 | 조사 노트만 추가된 체크리스트 게임으로 남음 |
| P1 | 미션 제작 형식, 장기 상태, 본편 끝까지 연결 | 앞 챕터를 반복 제작하고 후반 결말이 계속 밀림 |
| P2 | 챕터 3~12의 콘텐츠, 역할·회사 분기, 최종 대본 | 본편 분량과 선택의 후속 결과가 부족함 |
| P3 | 추가 장식, 선택 사건의 고유 연출, 부가 수집 요소 | 기본 플레이를 검증하기 전 제작 범위가 커짐 |

P3는 중요하지 않다는 뜻이 아니라 필수 플레이가 완성된 뒤 배치할 항목이다. 접근성, 번역과 저장 검증은 장식으로 분류하지 않는다.

## 마일스톤 0 현재 기반을 안정화한다

**결과물:** 최근 변경을 포함한 첫 챕터의 통합 검증 기록과 저장·진행의 기준점.

- 기존 66개 검사와 별도로 첫 출근에서 엔딩까지 실제 플레이한다.
- 쿠폰 결함을 발견한 경로와 놓친 뒤 핫픽스한 경로를 확인한다.
- 가설을 기록하지 않거나 바꾼 경우, 힌트를 많이 쓴 경우도 진행한다.
- 미션 도중 저장·종료·재개, 언어 변경, 새 게임 전환을 확인한다.
- 저장 버전과 일회성 결과의 중복 방지 기준을 정의한다.
- 검증된 변경과 남은 문제를 분리해 Git 기준점을 남긴다.

**완료 조건:** 확인한 경로에서 진행 막힘과 중복 보상이 없고, 저장과 실제 저장소가 다를 때 조용히 덮어쓰지 않는다. 발견된 문제에는 재현 방법과 처리 순서가 남아 있어야 한다.

이 단계에서 치명적인 저장 문제가 발견되면 챕터 2 제작보다 먼저 고친다. 새 기능의 연출만 어색한 문제는 명시적으로 남기고 핵심 진행 작업을 계속한다.

## 마일스톤 1 챕터 2에서 첫 재미를 확인한다

**결과물:** C02 M01~M03을 연결한 짧은 내부 플레이 구간.

지원 티켓에서 빠진 정보를 찾고, 지연과 재시도를 바꿔 중복 주문을 재현하고, 순차 요청의 중복 방지를 실제 코드로 수정한다. 위키를 읽었다는 기록을 넘어 재현 조건이 바뀌면 결과도 달라지는 작은 실험을 만든다.

단계별로 한 가지 새 개념만 소개한다. UI의 실험 조건과 테스트 입력은 같은 의미를 가져야 한다. 코드에서 구현한 결과가 게임 화면의 주문 수와 식별자에 반영돼야 한다.

이 구간은 순차 요청 계약을 검증하는 부분이며 고객의 중복 주문 전체를 해결했다고 선언하지 않는다. 동시 요청과 생성 실패 복구는 다음 업무의 명시적인 과제로 남긴다.

**완료 조건:** 설명을 따라 하기만 한 플레이어도 입력, 실제 결과와 기대 결과의 차이를 이해할 수 있다. 직접 해결, 힌트, 동료 페어링의 경로가 모두 같은 계약을 검증한다. 처음부터 코드를 읽고 해결한 숙련자에게 불필요한 단서 수집을 강제하지 않는다.

내부 검증에서는 조사보다 도구 사용법에 오래 막히는지, 원인을 고른 이유를 설명할 수 있는지, 수정 전후가 보이는지 확인한다. 이 단계에서는 아직 외부 배포를 하지 않는다.

## 마일스톤 2 챕터 2를 완결하고 선택을 만든다

**결과물:** 8개 업무와 고객 답장까지 이어지는 챕터 2, 최소 한 업무의 세 가지 접근.

- 로그 최소화, Sophie와의 화면 합의, 동시 요청과 실패 복구를 구현한다.
- 제한 적용, 관찰, 되돌리기와 고객 설명을 연결한다.
- 빠른 제한 적용, 충분한 사전 검증, 동료 병렬 조사 중 무엇을 먼저 할지 고르게 한다.
- 각 접근이 먼저 주는 정보와 적용 범위, 쓰는 시간, 동료의 작업을 다르게 만든다.
- 휴식과 컨디션을 정리하고 합의한 휴식을 업무 회피와 구분한다.
- 이미 익힌 브랜치·테스트·PR 절차의 반복 안내를 접고 필요한 도구로 이동하기 쉽게 한다.

**완료 조건:** 세 접근 모두 실제로 완료할 수 있고 한 가지가 항상 우월하지 않는다. 가설 선택만으로 일이 끝나지 않으며, 실제 코드 검증과 고객 결과가 연결된다. 되돌리거나 도움받은 경로에도 충분한 마무리가 있다.

첫 챕터부터 챕터 2 말까지 저장·재개가 이어져야 한다. 기존의 전환 또는 이직 엔딩 세이브도 연결 장면으로 진입할 수 있어야 한다. 챕터 2 말에서 후반 챕터가 구현된 것처럼 잘못 안내하지 않는다.

## 마일스톤 3 외부 테스트 가능한 Windows 빌드를 만든다

**결과물:** 개발 도구가 설치되지 않은 별도 Windows 환경에서 실행할 수 있는 테스트 빌드.

실행 환경 조사와 작은 검증은 마일스톤 0부터 시작할 수 있다. 내부 플레이 개선과 별도로 실패 위험을 일찍 확인하되, 외부 배포의 통과 조건은 이 마일스톤에 둔다.

- 동봉할 Git·Node 버전과 호출 경로, 배포 파일과 고지를 정리한다.
- 플레이어 코드가 실행되는 Windows 격리 수단을 작은 프로토타입으로 검증한다.
- Node 테스트 실행뿐 아니라 Git이 호출하는 하위 프로세스와 사용자 환경의 영향을 점검한다.
- 시간 제한, 과다 출력, 자식 프로세스, 강제 종료와 재시작 후 복구를 확인한다.
- `content`의 TypeScript, 테스트, 텍스트와 양쪽 언어 자료를 export에 포함한다.
- 시스템 PATH의 Git·Node를 사용할 수 없는 별도 환경에서 확인한다.
- 저장 백업과 복구 안내, 빌드 번호와 문제 재현 자료를 준비한다.

**완료 조건:** 깨끗한 환경에서 설치·실행·저장·재개·정상 종료가 가능하며, 코드 실행이 허용 영역을 벗어나지 않는다는 검증 근거가 있다. 가상 경로 표시나 타임아웃만으로 격리 완료를 판정하지 않는다.

격리 프로토타입이 성립하지 않으면 안전한 실행 방식을 먼저 조정한다. 해결 전 빌드를 외부 플레이테스터에게 배포해 문제를 뒤로 넘기지 않는다.

## 마일스톤 4 소규모 플레이테스트로 제작 범위를 확정한다

**결과물:** 관찰 기록, 수정 우선순위, 챕터당 실제 제작 시간과 플레이 시간.

개발 경험이 적은 사람과 있는 사람을 섞어 처음에는 5명 정도를 대상으로 형성 평가를 한다. 소규모 결과는 문제를 찾는 자료로 사용하며 시장 반응을 대표한다고 보지 않는다. 실제 모집과 빌드 전달은 별도 실행 작업이다.

| 관찰할 것 | 1차 통과 기준 |
|---|---|
| 다음 행동 이해 | 5명 중 4명이 현재 문제와 다음 확인 행동을 자신의 말로 설명 |
| 추리와 검증 연결 | 최소 3명이 수정 전후의 차이와 가설을 연결해 설명 |
| 선택의 의미 | 최소 3명이 두 접근의 이득과 비용을 구분 |
| 도움의 효과 | 막힌 사람이 힌트나 페어링 후 다음 행동으로 복귀 |
| 안정성 | 진행 불가, 저장 손실, 외부 환경 의존 문제 0건 |
| 반복 피로 | 같은 불필요 작업이 반복 지적되면 콘텐츠 확장 전 수정 |

관찰에는 어디서 멈췄는지와 그 이유를 함께 적는다. 오래 생각한 시간을 무조건 나쁜 지표로 보지 않는다. 규칙을 추리한 시간과 조작법을 몰라 기다린 시간을 구분한다.

**완료 조건:** 위 기준에 못 미친 원인이 단서, 규칙, UI, 난이도 중 어디에 있는지 설명되고 중요한 문제가 수정됐다. 실제 제작 시간으로 장편 범위와 출시 일정의 첫 추정치를 다시 만든다.

## 마일스톤 5 본편을 끝까지 이어 붙인다

**결과물:** 챕터 1에서 12까지 진입·전환·결말이 이어지는 내부용 본편 골격.

- 챕터, 실행 일차, 서사 날짜와 역할을 분리한 진행 구조를 확정한다.
- 미션·대사·정책·검증·장기 효과를 제작하는 공통 형식을 만든다.
- 장기 상태에는 결과의 출처와 보완 내역을 남긴다.
- 회사와 역할 분기, 동료 이동, ATLAS 결과와 진로 후일담을 연결한다.
- 핵심 대표 업무와 장면을 각 챕터에 하나씩 먼저 놓고 인과관계를 확인한다.
- 아직 없는 콘텐츠는 내부용 표시로 명확히 구분하고 출시판 분량으로 계산하지 않는다.

**완료 조건:** 서로 다른 소속과 역할에서 첫 출근부터 마지막 신입 PR까지 내부 경로가 연결되고, 필요한 증거를 얻을 방법이 있다. 누락된 콘텐츠가 목록으로 보이고 결말의 원인과 결과를 설명할 수 있어야 한다.

마지막 챕터를 제작 마지막까지 비워 두지 않는다. 결말을 먼저 연결해 초반의 선택이 실제 후일담에 사용되는지 확인한다.

## 마일스톤 6 장편 콘텐츠를 세 묶음으로 완성한다

| 묶음 | 범위 | 중심 플레이 | 해당 묶음의 통과 조건 |
|---|---|---|---|
| A | 챕터 3~5 | 기능 출시, 기술 부채, 성수기 운영, 이직 선택 | 전환 면담과 실제 오퍼 과정이 자연스럽고 예방·수습 경로 모두 완료 |
| B | 챕터 6~9 | 회사별 업무, 멘토링, AI 검토, 조직 개편 | 소속·역할·동료 이동에 따라 실제 담당과 작업이 달라짐 |
| C | 챕터 10~12 | 공동 계약, 전환 판단, 인계, 진로 선택 | 전환 완료·단계 적용·복귀가 각각 결말로 이어짐 |

각 묶음에서 대사, 코드·테스트, 한글·영문, 힌트, 저장 지점과 후속 결과를 같이 완료한다. 한국어 본편을 다 만든 뒤 영어와 재개 문제를 한꺼번에 처리하지 않는다.

완성한 조사와 검증 도구는 후반의 반복 작업을 줄인다. 첫 주문 대조를 수동으로 해 봤다면 나중에는 만든 도구의 보고서를 읽고 차이에 집중한다. 성장의 효과를 숫자 보너스보다 실제 작업 변화로 보여준다.

**완료 조건:** 96개 업무 슬롯과 선택 사건이 계획상 개수만 채우는 것이 아니라 서로 다른 판단과 결과를 제공한다. 줄여야 할 때는 반복 업무와 일회성 연출부터 조정하고 본편의 인과와 결말을 보존한다.

## 마일스톤 7 출시 후보를 검증한다

**결과물:** 기능을 고정한 출시 후보 빌드와 검증 기록.

- 소속 2개, 두 번째 이동 여부 2개, 역할 2개, ATLAS 결과 3개의 기본 24조합을 검토한다.
- 모든 진로 결말이 적합한 조건에서 열리는지 별도로 확인한다.
- 낮은 친밀도, 많은 도움 사용, 초반 실패 후 회복, 주요 동료 이동을 경계 사례로 추가한다.
- 저장 손상·이전 버전·중간 종료·언어 전환과 Git 상태 불일치를 확인한다.
- 키보드 조작, 글자 크기, 색 외의 상태 구분, 시간제한 완화, 효과·음량을 확인한다.
- 깨끗한 Windows 환경과 실제 배포 파일에서 전체 진행을 확인한다.
- 구현된 기능과 분량을 기준으로 스토어 설명, 스크린샷과 예고편을 만든다.
- 제출 시점의 공식 Steamworks 자료로 최신 제출 절차와 필요한 항목을 확인한다.

**완료 조건:** 진행 불가·저장 손실·권한 및 실행 영역 이탈·핵심 분기 단절이 0건이고, 남은 문제의 영향이 공개 가능한 수준으로 정리돼 있다. 출시 후보에 새 시스템을 계속 추가하지 않는다.

이 계획은 현재 Steam의 구체적인 제출 요건을 확정하지 않는다. 스토어 등록 준비와 공개·빌드 제출은 각각 실제 자료를 갖춘 별도 작업으로 진행한다.

## 일정 관리

현재 인력과 실제 제작 속도가 확정되지 않았으므로 출시일을 먼저 약속하지 않는다. DEV 004~006에서 대본·코드·번역·검증에 각각 쓴 시간을 기록하고, 챕터 2가 끝났을 때 1차 일정을 산정한다.

일정에는 콘텐츠 작성뿐 아니라 수정, 번역 검수, 새 환경 검사와 플레이테스트 반영 시간을 포함한다. 각 마일스톤은 완료 기준을 통과한 뒤 다음 상태로 이동한다. 외부 테스트와 실제 제출은 필요한 상대와 계정 상태를 확인한 뒤 일정에 넣는다.

운영 상태는 다음 세 칸으로 관리한다.

- **지금:** 챕터 2 전체 플레이테스트, 실제 플레이 시간과 막힌 지점 기록.
- **다음:** 고객 질문 분기·동료 페어링 보강, 로그·화면 상태·동시 요청 업무, 수동 UI와 런타임·격리 검증.
- **이후:** 외부 테스트 빌드, 챕터 3(LEGACY-17)과 장편 콘텐츠 제작.
